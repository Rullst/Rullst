Três frameworks web em Rust. Fatos verificados.

Rullst, Loco e Topcoat.

Os três constroem aplicações web em Rust sobre o Tokio, e cada um é a melhor escolha para alguns projetos. Esta página compara os três tema a tema, com base no que a documentação de cada projeto diz. Quando um projeto não documenta algo, a página diz isso em vez de adivinhar.

Verificado em 14 de novembro de 2026 com Rullst 13.0.0-alpha.5, Loco loco-rs 1.3.1 e Topcoat topcoat 0.12.1. Quem escreveu esta página é o mantenedor do Rullst. Se algum fato estiver errado ou desatualizado, abra uma issue.

Quando cada um faz sentido

  • Rullst

    Faz sentido quando você quer uma suíte coordenada sobre Axum e SQLx que já traga sessões e passkeys, proteção contra CSRF, cobrança (Stripe e InfinitePay), e-mail transacional, um admin de modelos e uma sala de controle local para desenvolvimento, com HTML renderizado no servidor.

    Leve em conta: a 13.0 ainda é um pré-lançamento, e o projeto foi publicado pela primeira vez em maio de 2026 pelo seu único mantenedor.

  • Loco

    Faz sentido quando você quer uma versão 1.x estável com convenções no estilo Rails, Sea-ORM, autenticação por JWT ou cookie, filas de jobs em Redis, PostgreSQL ou SQLite e geradores de modelos, scaffolds e workers. É a maior comunidade dos três.

    Leve em conta: pagamentos e uma interface de admin não fazem parte da documentação dele.

  • Topcoat

    Faz sentido quando você quer componentes renderizados no servidor cujas expressões $(...) também rodam no navegador como JavaScript gerado, sem bundle Wasm e sem etapa de build no cliente.

    Leve em conta: o README o descreve como inicial e experimental; autenticação, jobs em segundo plano e documentação de deploy estão no roadmap dele.

Tema a tema

Modelo de renderização

Rullst
HTML renderizado no servidor pela macro html!, com escape por padrão, e htmx e a build CSP do Alpine.js para interatividade. Sem bundle no cliente por padrão.
Loco
Templates no servidor com Tera 2, por trás de um renderizador substituível. Também um modo SPA no cliente (Vite e React) e um modo de binário único com assets embutidos.
Topcoat
Renderização no servidor com a macro view! e componentes assíncronos. As expressões $(...) são Rust com checagem de tipos, também traduzido para JavaScript para dar reatividade no navegador. Integrações opcionais com htmx, Alpine AJAX e Datastar.

Banco de dados e ORM

Rullst
ORM próprio (#[derive(Orm)]) sobre SQLx para SQLite, PostgreSQL e MySQL/MariaDB, com migrações Schema. Turso/libSQL, SurrealDB e estruturas de dados do Redis por adaptadores separados.
Loco
Sea-ORM 2.0 com migrações. Os drivers de banco documentados são SQLite e PostgreSQL.
Topcoat
Sem ORM no crate topcoat. topcoat new --database toasty gera uma aplicação que usa o Toasty sobre SQLite, com as migrações do Toasty.

Autenticação e segurança padrão

Rullst
Hash de senha com Argon2, sessões criptografadas, passkeys, RBAC e login OAuth2/OIDC. O starter SaaS já liga o middleware de CSRF; o rullst-security também oferece cabeçalhos seguros, uma camada de WAF e bloqueio de login.
Loco
JWT por padrão, com hash argon2 e chaves de API. Sessões em cookie assinado ou criptografado e OAuth2/OIDC com presets de GitHub e Google são opcionais. O middleware de cabeçalhos seguros existe, mas vem desligado; middleware de CSRF não está documentado.
Topcoat
Tokens de sessão com armazenamento fornecido por você, em cookies __Host-, Secure, HttpOnly e SameSite=Lax. Uma política de origem padrão rejeita requisições de outras origens que alteram estado. Autenticação está no roadmap; hash de senha, cabeçalhos seguros e tokens de CSRF não estão documentados.

Jobs em segundo plano

Rullst
Filas no rullst-core (em processo, SQLite e Redis). O rullst-messaging acrescenta novas tentativas, filas de mensagens mortas, um relay de outbox e mensageria com Redis Streams.
Loco
Filas em Redis, PostgreSQL ou SQLite, modos em processo e um agendador no estilo cron.
Topcoat
Não há suporte embutido. Jobs em segundo plano estão no roadmap.

E-mail

Rullst
rullst-mail: e-mail com templates via Resend, AWS SES, SendPulse ou SMTP, entregue em segundo plano, com supressão de destinatários e um kit de conformidade para o seu próprio transporte.
Loco
Um mailer SMTP embutido que envia pela fila de jobs, com um modo stub para testes. Um recurso opcional de notificações acrescenta Slack e webhooks.
Topcoat
Um recurso opcional de e-mail com transportes SMTP, arquivo (.eml) e em memória.

Pagamentos e cobrança

Rullst
rullst-capital: adaptadores Stripe e InfinitePay, webhooks verificados com proteção contra replay, cotas, direitos de acesso e faturas.
Loco
Não documentado.
Topcoat
Não documentado.

Admin e observabilidade

Rullst
Nexus, um admin gerado para os modelos registrados; Studio, uma sala de controle local para desenvolvimento; exportação de traces distribuídos via OpenTelemetry, testada na CI com um OpenTelemetry Collector em um contêiner local.
Loco
Nenhuma interface de admin documentada. Logs com tracing, endpoints /_ping, /_health e /_readiness e cargo loco doctor.
Topcoat
Sem framework de admin (existe uma aplicação de demonstração de admin). Logs e endpoints de saúde não estão documentados; a geração de OpenAPI chegou na 0.12.1.

CLI e geradores

Rullst
cargo rullst new (starters Blank, API e SaaS) e geradores make:* para modelos, migrações, controllers, resources, workers, e-mail, cobrança, MFA, OAuth e outros; dev, doctor e upgrade assistido.
Loco
loco new (templates SaaS, REST API, lightweight e advanced) e cargo loco generate para modelos, migrações, scaffolds, controllers, tasks, workers, mailers e arquivos de deploy.
Topcoat
topcoat new, dev, fmt, ui (copia componentes para o projeto), asset bundle e l10n check. Geradores de modelos ou controllers não estão documentados.

Orientação de deploy

Rullst
Guias para DigitalOcean, Hetzner, Oracle Cloud e Google Cloud. A CI testa o deploy gerado para VM dos starters Blank e SaaS, com SQLite, no Docker e no Podman em um runner x86_64; máquinas Arm não são testadas, e os guias dos provedores foram escritos a partir da documentação deles, sem serem seguidos de ponta a ponta em contas reais.
Loco
Um binário de release, mais configurações geradas de Docker, nginx ou AWS Lambda, e loco doctor antes de ir para produção.
Topcoat
A documentação de deploy está no roadmap. Há um exemplo para Cloudflare Workers e hospedagem própria via serve() ou Router::handle.

Estabilidade, versionamento e janela de suporte

Rullst
A 13.0 está em pré-lançamento; a 13.0.0-alpha.6 congelou as funcionalidades e a API pública, e a 13.0.0-rc.1 traz correções, documentação e as mudanças que o mantenedor aprovou uma a uma depois do congelamento, duas delas incompatíveis. Depois da 13.0.0, o mantenedor pretende manter a 13.x como linha ativa por 12 meses e, depois da 14.0.0, dar a ela correções de segurança por mais 1 a 3 meses (uma intenção, não uma garantia). Versionamento semântico; MSRV Rust 1.96.
Loco
A 1.0.0 (julho de 2026) foi a primeira versão estável. As notas de atualização listam mudanças incompatíveis; uma declaração de semver e uma janela de suporte não estão documentadas. MSRV Rust 1.94.
Topcoat
O README diz: inicial e experimental, espere mudanças incompatíveis. O changelog diz que segue o versionamento semântico. Nenhuma janela de suporte documentada. MSRV Rust 1.99.

Por que não Leptos ou Dioxus?

Verificado em 19 de novembro de 2026 com Leptos leptos 0.8.23 e Dioxus dioxus 0.7.10.

Leptos e Dioxus são full-stack em outro sentido: são frameworks de interface. Os mesmos componentes Rust podem renderizar HTML no servidor e depois rodar no navegador como WebAssembly, que hidrata esse HTML, e as server functions permitem que o navegador chame código Rust que roda só no servidor. O Dioxus também tem como alvo desktop e dispositivos móveis.

Por serem frameworks de interface, nenhum dos dois traz ORM, migrações ou autenticação, e nenhum documenta e-mail, jobs em segundo plano ou painel de admin. O livro do Leptos diz que o próprio Leptos não fornece nem o servidor HTTP nem o banco de dados; a documentação do Dioxus diz que ele não oferece uma forma embutida de gerenciar autenticação, e o tutorial de banco de dados dele usa o rusqlite e cita SQLx e SeaORM entre as alternativas. As aplicações montam essas partes com outros crates: o exemplo de autenticação do Leptos e o guia de autenticação do Dioxus usam o axum_session_auth com SQLx.

Eles não estão na seção Desempenho porque ela mede aplicações equivalentes atendendo requisições HTTP. O lado servidor de uma aplicação Leptos roda sobre Actix Web ou Axum, pelas integrações do Leptos, e o Dioxus Fullstack é construído sobre o Axum, que já é a referência do benchmark; uma aplicação equivalente ainda precisaria de ORM e autenticação montados à mão. As abordagens se complementam: uma interface em Leptos ou Dioxus pode consumir uma API HTTP do Rullst.

Desempenho

Estes números não são escritos à mão: cada build diário deste site insere os resultados publicados mais recentes da suíte Rullst/Benchmarks para os três frameworks, o Actix Web e o Gin, além de uma configuração mínima do Rullst. O mantenedor do Rullst também mantém esse benchmark e escreveu todas as implementações dele.

Como ler estes números

  • 1,00× é o Axum. Cada pontuação divide o resultado de um framework pelo resultado do Axum, um framework Rust pequeno usado como referência, medido na mesma máquina em rodadas alternadas. 0,50× é metade do resultado do Axum e 2,00× é o dobro. Mais é melhor em todas as pontuações: em memória e tempo de inicialização a razão é invertida, então uma pontuação maior significa menos RAM ou uma inicialização mais rápida.
  • Empates e ±. As máquinas são máquinas de nuvem compartilhadas, então os resultados variam de uma execução para outra. "±6%" ao lado de uma pontuação é a margem dentro da qual duas pontuações não podem ser distinguidas. Pontuações tão próximas dividem um intervalo de posições, como "3–7": essas implementações estão nas posições 3 a 7, sem ordem entre elas.
  • As categorias respondem a perguntas diferentes. Hello world: quanto um framework custa por requisição quando a página é trivial. Banco de dados: como ele lê, grava e renderiza linhas. Aplicação: o que ele faz com uma requisição real (entrada, validação, uma gravação, um formulário com proteção contra CSRF, um usuário autenticado). Memória: quanta RAM ele precisa sob carga. Inicialização: quão rápido ele inicia. Estabilidade (passou ou falhou): se ele continua funcionando sob carga mais pesada.
  • O banco de dados costuma vir primeiro. Numa aplicação real, o banco de dados costuma ser o limite antes do framework, então uma diferença grande em Hello world diminui ou desaparece quando as requisições leem e gravam dados; Banco de dados e Aplicação estão mais perto do que uma aplicação faz.
  • A pontuação geral é um resumo. Ela combina as cinco pontuações de categoria, com Hello world, Banco de dados e Aplicação contados duas vezes e Memória e Inicialização uma vez, para uma leitura rápida. As categorias são o resultado de verdade: outros pesos mudam a ordem, como mostram os resultados completos.
  • O Rullst aparece duas vezes. "Rullst" é a aplicação que o cargo rullst new gera, com o middleware de produção que ele liga: WAF, proteção contra CSRF, cookies seguros, cabeçalhos seguros e log de acesso; é o Rullst com posição. "Rullst (mínimo)" usa o mesmo roteador, o mesmo ORM e os mesmos templates html! sem essas camadas, servido como o app do Axum; é um diagnóstico, com pontuações e sem posição. A diferença entre as duas linhas é o custo dessas camadas.

Não há resultados atuais disponíveis. Esta seção se preenche automaticamente quando o Rullst/Benchmarks publicar resultados que esta página consiga ler; até lá, ela não mostra números, em vez de mostrar números antigos.
