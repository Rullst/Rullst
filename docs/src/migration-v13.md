# Preparing an application for v13

**The current source is `13.0.0-rc.2`, a prerelease, not a stable v13
release.** The first prerelease, `13.0.0-alpha.1`, was published on October 11, 2026.
The 12.x line, on the frozen `v12` branch, reached end of life on 16 October
2026 with 12.3.0 as its last release; `main` develops v13. The development packages use the same v13
version and internal requirements. `rullst-privacy`, `rullst-supervision`,
`rullst-media` and `rullst-labs` join the candidate package inventory and were
first published in 13.0.0-alpha.1. Privacy
has explicit `privacy-*` umbrella features; Supervision, Media and Labs remain
standalone opt-ins.
All twenty packages are published together as each v13 prerelease; the current
one is `13.0.0-rc.2`. Cargo never selects
a prerelease on its own, so `cargo add rullst` still selects the end-of-life
12.3.0: opt in with
an exact requirement such as `rullst = "=13.0.0-rc.2"`. A plain
`"13.0.0-rc.2"` is a caret requirement that also accepts later prereleases, which
may break the API. From 13.0.0-alpha.2 the CLI writes the `=` form; a project
generated by the 13.0.0-alpha.1 CLI has the caret form, so add the `=` to its
`rullst` and `rullst-orm` lines. Since 13.0.0-alpha.3 `rullst` and
`rullst-orm` have no default features and compile no SQLx driver on their own,
so a hand-written manifest selects the database profile it uses, as
`cargo rullst new` does (see the Minimal default features row):

```toml
rullst = { version = "=13.0.0-rc.2", default-features = false, features = ["strict-postgres"] }
```

This inventory covers the `13.0.0-rc.2` development source. Revisit it as the remaining
[delivery priorities](v13-delivery-plan.md) land. It does not promise that every
existing application, provider account or deployment works without review.

Install the CLI of the version you upgrade to before running
`cargo rullst upgrade`, and check what `rullst --version` prints: a CLI
already on `PATH` may be an earlier prerelease, which targets its own version
by default and does not know the rules of later releases:

```bash
cargo install cargo-rullst --version =<version> --locked --force
rullst --version
```

To find the rows that affect an application, run `cargo rullst upgrade --dry-run`
with the v13 CLI: its `rullst-upgrade-rules-v4` catalog reports `MUST-CHANGE`
and `REVIEW` findings at `file:line`, each naming the first-column title of its
row below, with the guidance to apply by hand. The
[assisted upgrade tutorial](tutorials/36-assisted-framework-upgrades.md#v12-to-v13-source-findings)
describes the workflow and [classifies every row](tutorials/36-assisted-framework-upgrades.md#v12--v13-rule-classification).
Rows without rules still need a reading. An application already on a 13.0
prerelease gets only the rules introduced after its version, and the plan says
how many earlier rules it skipped; `--all-rules` applies every rule, and
`--from <VERSION>` the rules introduced after that version, for an application
that already pins the target version (whose plan warns that the target's own
rules did not run; since the 13.0.0-rc.1 CLI)
([rules by release](tutorials/36-assisted-framework-upgrades.md#rules-by-release)).
An application that already runs 13.0.0-rc.1 follows the
[rc.1 to rc.2 checklist](#upgrading-an-rc1-application-to-rc2); one on
13.0.0-alpha.6 follows the shorter
[alpha.6 to rc.1 checklist](#upgrading-an-alpha6-application-to-rc1) first; one on
13.0.0-alpha.5 follows the
[alpha.5 to alpha.6 checklist](#upgrading-an-alpha5-application-to-alpha6)
first; one on 13.0.0-alpha.4 follows the
[alpha.4 to alpha.5 checklist](#upgrading-an-alpha4-application-to-alpha5)
first, one on 13.0.0-alpha.3 the
[alpha.3 to alpha.4 checklist](#upgrading-an-alpha3-application-to-alpha4)
before that, and one on 13.0.0-alpha.2 the
[alpha.2 to alpha.3 checklist](#upgrading-an-alpha2-application-to-alpha3)
before those.

Three things outside the Rust code change with every upgrade:

- **Pinned CLIs.** Workflows and scripts that install a pinned CLI
  (`cargo install cargo-rullst --version =…`, often through a
  `RULLST_CLI_VERSION` variable) need the new version, whatever the workflow
  file is called: `grep -rn 'RULLST_CLI_VERSION\|cargo-rullst' .github/workflows`
  lists them. `cargo rullst upgrade` does not edit them.
- **Other copies of the version.** After the upgrade, search the repository
  for the previous version string (`grep -rn <old-version> .`, skipping
  `target/`): CI files that install `cargo-rullst`, README badges,
  deployment documentation, and kits or generated projects that embed a
  Rullst manifest and lockfile keep the old one. Inside them, change the
  manifest pins and run `cargo update -p <a Rullst package the project
  depends on> --precise <version>`.
- **Lockfiles.** `cargo update -p rullst --precise <version>` (or the
  upgrade itself) can rewrite a large part of `Cargo.lock`: the new
  prerelease's requirements re-resolve shared dependencies, so dozens of
  packages may be added, removed or moved to another major (13.0.0-alpha.6
  brought `jsonwebtoken` 12 and `jiff`). That is expected; review it like any
  dependency update. A `Cargo.lock` the application ships as content, such
  as a starter kit or a course project, is updated with Cargo too: change
  the kit's `Cargo.toml` requirement, then run
  `cargo update --manifest-path <kit>/Cargo.toml -p rullst --precise <version>`.
  Never replace the version strings in the lockfile's text: its `checksum`
  lines would no longer match the registry, and Cargo refuses the file.

## Changes from the published 12.1.0 source

| Area | Application impact |
| :--- | :--- |
| Existing runtime APIs | Source preparation changes supported dependency requirements; it invents no Rust rewrites. Review the explicit account-session schema migration below even when existing Rust calls still compile. |
| Account/session registry | Before serving requests with the new Auth recovery store, explicitly run `SqlRecoveryStore::migrate()` to add session details and the expiry index. Existing opaque sessions remain valid with unknown historical metadata. Configure expired-session maintenance and authorize new inventory/logout routes; see [session management](session-management.md). The CLI manifest updater does not apply this SQL migration. |
| Server-side login sessions | Opt-in, since 13.0.0-alpha.6. A `make_login_cookie_with_epoch` cookie stays valid after sign-out until it expires; to make sign-out end every copy and to list and sign out devices, enable `auth-session-registry-sqlite`, `-postgres` or `-mysql` (the facade feature of your strict database profile), add a migration whose `up` calls `rullst::auth::session_registry::SessionRegistry::create_table(pool)` and whose `down` drops `rullst_auth_sessions`, then `SessionRegistry::connect` over your SQLx pool at startup (or `SessionRegistry::open`, which creates the table on first use instead), issue cookies with `sign_in` (or `create_session`), check them with `authenticate_request` in your authentication middleware (keep comparing the session epoch from `claims()`), sign out with `sign_out`, and call `revoke_all_sessions` where you bump the epoch (password change and reset, sign out everywhere, deactivation). Cookies issued before the switch are refused, so every user signs in once more; to avoid that, accept `decrypt_session_claims` cookies beside registry cookies for at most their remaining lifetime (30 days by default). Schedule `purge_expired`. For Server-Sent Events and WebSockets, pass `revalidation(session.current())` to `RealtimeSse::channel_revalidated` or `WebSocket::with_revalidation` so they end when the session does. Projects generated by `cargo rullst auth` or the SaaS starter before 13.0.0-alpha.6 keep epoch cookies; new ones use the registry, and `cargo rullst upgrade` reports each call that still issues or accepts an epoch cookie, in any file outside tests: while no manifest enables a registry feature (`V13-AUTH-SESSION-REGISTRY`), and, once one does, because the registry's middleware refuses those cookies at run time (`V13-AUTH-SESSION-EPOCH-CALLS`, since the 13.0.0-rc.1 CLI). See [session management](session-management.md#server-side-login-sessions). |
| Private object storage | The optional `storage-s3` candidate requires explicit signing credentials and production validation. Existing cloud constructors stay unconfigured; no bucket, IAM policy or credentials are inferred. See [private storage](private-object-storage.md). |
| R2 public URLs | `Storage::r2(...).url(key)` (and `TenantStorage::url` over R2) now returns `StorageError::Unsupported` instead of `https://<account>.r2.cloudflarestorage.com/<bucket>/<key>`. That S3 API endpoint requires a signature for every request, so the URL never loaded in a browser. Build public URLs from your `r2.dev` or custom domain in the application, or use a signed download with `storage-s3`. |
| Tenant local storage | `TenantStorage` reads, metadata and deletes on local storage return `StorageError::Io` when the tenant directory lies below a regular file (for example a file named `tenants` in the base path), on every platform. On Windows, 12.x and 13.0.0-alpha.1 returned `NotFound` there, as if the object were missing. |
| Distributed tracing | Opt in to `telemetry::distributed` with approved operation names, upstream trust, a collector and owned flush/shutdown. The legacy initializer now uses compatible threaded OTLP/HTTP export and defaults to `127.0.0.1:4318/v1/traces`; `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL, while `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is exact. Redirects and request bodies over 1 MiB are unsupported; the legacy initializer exports at most 64 spans per request (unless `OTEL_BSP_MAX_EXPORT_BATCH_SIZE` is set), honours `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` and reports dropped batches on stderr, while the minimized profile ignores proxy variables. Review existing collector environment configuration; [the tracing guide](distributed-tracing.md) distinguishes both metadata policies. |
| Core queue | SQLite claims jobs in due-time order, so a due scheduled or handed-back job no longer waits behind later immediate jobs, and `retry_failed_job` keeps the attempt counter (it fences claims) instead of resetting it to 0. A job no worker has a handler for is failed with `HandlerNotFound` at its 720th claim attempt instead of being handed back forever. `dispatch`/`dispatch_at` reject empty names and names over 256 bytes, and `Worker::run` rejects `job_timeout(Duration::ZERO)`, all with `QueueError::InvalidConfiguration`. Redis queue commands wait up to 10 s for a reply instead of 500 ms. Stalled recovery of a claim made without a lease (SQLite `pop`) may now happen up to two seconds after `stalled_after`, never before. Failed jobs that a 12.x process records in a Redis queue, including 12.x workers during a rolling upgrade, are not in the new failed-job index: they are neither counted nor evicted by the 10,000-entry retention, so retry them with `retry_failed_job` or remove them with `purge_failed_jobs` once every worker runs 13. |
| Core scheduler, cache and realtime | `Scheduler::start` returns the new `SchedulerError::InvalidConfiguration` for a zero task timeout; exhaustive matches in other crates are unaffected because the enum is `#[non_exhaustive]`. The Redis cache treats a zero TTL as an already-expired value (the key is removed) and a TTL beyond Redis's expiry range as no expiry, as the memory driver does. `PresenceTracker` counts connections: call `user_left` once per `user_joined`, since a user stays online until the last leave. `Channel::new` clamps the capacity to 65,536. The Traffic Shield database probe gives up at `max_db_latency` and records at least that latency. A Live recovery session no longer counts its own callback and send time as peer silence. `TenantCache` now writes `%` as `%25` and `:` as `%3A` in the tenant segment of its keys (`tenants:a%3Ab:<key>`), so entries of tenant IDs containing those characters start cold, and while 12.x and 13 instances share the cache a `forget` on one version does not remove the other's entry for such a tenant; rely on TTLs or finish the rollout before depending on invalidation. |
| Core memory cache sweeps | `Cache::memory()` sweeps expired entries after a number of operations equal to a quarter of the entries the previous sweep kept (at least 256), instead of every 256 operations, so the sweep cost per request no longer grows with the cache. Reads still never return an expired value; unread expired entries may stay in memory longer in a large cache. |
| Studio queue monitor | Studio lists queue records with the new `QueueDriver::list_job_previews` (at most 2 KiB of each payload and error) instead of `list_all_jobs`. Custom drivers keep working through the default projection of `list_all_jobs`; override `list_job_previews` to cut values in the store. |
| Studio API playground | `Studio::with_openapi` took a utoipa 6 `OpenApi` from 13.0.0-alpha.1 to alpha.5; since 13.0.0-alpha.6 it takes any `serde::Serialize` document, so a document built with utoipa 5 works again (Studio OpenAPI documents row). Studio no longer embeds Swagger UI (its `utoipa-swagger-ui` build dependency needs a `zip` release that crates.io has yanked): `/studio/api` is now a server-rendered, read-only reference of the operations, `/studio/api/` redirects to it and `/studio/api/openapi.json` still serves the document. There is no in-page "Try it out"; send requests with an external client. |
| Studio local access and table view | `LocalStudioAccess::loopback_only()` now accepts an IPv4-mapped loopback peer (`::ffff:127.0.0.1`, reported by a dual-stack `HOST=::` listener) instead of returning 403; other mapped addresses stay rejected. The table view, and the public `get_any_value_as_string`, now report a present value that no text, integer, float or Boolean codec decodes (for example a non-UTF-8 BLOB) as `unreadable` instead of `NULL`, and a stored text `NULL` is no longer styled as SQL NULL. |
| LMS blueprint | `--blueprint lms` now generates a small starter: catalog, modules, lessons, an accessible player, enrollment, owner-bound progress, login and a Nexus admin. The complete Academy scaffold (schools, roles, quizzes, activities, scores, automation, notifications, publication, privacy lifecycle) and `--lms-modules` were removed; existing generated applications keep their code. Registration no longer generates the school-membership hook, and the learner dashboard no longer claims a default demo school: it points to the course catalog. Since 13.0.0-alpha.4 this starter is the `examples/lms` application instead (see "CLI starters moved to the examples"). |
| Consumer generators | `make:supervision` was removed with the complete Academy LMS it targeted; integrate `rullst-supervision` directly. `make:privacy` and `make:age-gate` now target only the SaaS starter (`--blueprint saas`, which requires `--tenant-ref`). |
| `html!` event handlers | A dynamic value in an `on*`, `hx-on` or `hx-on-*` attribute (for example `onclick={handler}`) no longer compiles, because escaping cannot make data safe inside JavaScript. Static handler strings still compile; move data-driven handlers into a nonce'd script with `addEventListener` and pass values through `data-*` attributes. The default CSP already blocked such inline handlers. **Breaking**, from 13.0.0-alpha.5: the same holds for Alpine.js directives (`x-data={state}`, `x-show?={open}`, also `data-x-*`), which Alpine runs as JavaScript, and for the `@*`, `:*` and `hx-on:*` names that alpha.5 accepts; write them as static strings and pass server values through `data-*` attributes (`$el.dataset` in Alpine) or a `<script type="application/json">` data block. `cargo rullst upgrade` reports dynamic `x-*` values (`V13-HTML-DYNAMIC-ALPINE-DIRECTIVE`). |
| `html!` returns `Markup` | Since 13.0.0-alpha.2, `html!` returns `rullst::html::Markup` (escaped HTML) instead of `String`. Interpolating a `Markup` inserts it as HTML, so a fragment built by another `html!` call is no longer shown as escaped text and needs no `RawHtml`; `String`, `&str` and numbers are still escaped. A function declared `-> String` that returns `html!` no longer compiles: declare it `-> Markup`. `RawHtml(html! { .. })` no longer compiles: interpolate the `Markup` directly. Collect lists with `.collect::<Markup>()` (collecting `Markup` into a `String` does not compile) and use `Option<Markup>` for optional parts. `render_page`/`render_page_with_lang` take `impl Into<Markup>` (wrap a `String` of trusted HTML with `Markup::from_trusted`). A handler can return `Markup` (`text/html; charset=utf-8`), `Html(html! { .. })` still compiles, `Markup` compares with and reads like a `&str`, and `.into_string()` returns the `String`. See [`html!` returns `Markup`](#html-returns-markup). |
| Core request validation | `ValidatedForm`/`ValidatedJson` return 413 for oversized bodies and 415 for a wrong content type (HTMX requests receive the same code in `X-Rullst-Validation-Status`); other read failures stay 400. Nested errors are keyed `address.zip` and `items[0].name`, and `ValidationError` formatting no longer includes submitted values. Update clients or tests that expected 400 for these cases. |
| Core feature flags and scheduler | A user outside a declared A/B split now resolves to `"disabled"` instead of falling through to the next driver, and a negative database `rollout_percentage` means 0%. `Scheduler::task` uses POSIX weekday numbering (0 and 7 are Sunday) with the day-of-month OR day-of-week rule in UTC; review numeric weekdays in existing schedules. `RullstConfig::environment()` now reports the environment the Server enforces, including a value read from `.env`. Percentage rollouts and A/B variants of the Env, TOML, Memory and DB drivers use a versioned SHA-256 bucket hash instead of `std`'s `DefaultHasher`, so upgrading reassigns users to buckets once (percentages and variant weights are kept). End experiments whose assignment must not change before upgrading, and keep the period in which 12.x and 13 replicas both serve short, because they assign the same user differently. |
| Memory feature-flag splits | A `MemoryFeatureDriver::override_variants` flag (including `FeatureManager::overrides()`) no longer reports `enabled`/`enabled_for` as true for everyone. Like the Env, TOML and DB drivers, `enabled_for` is true only for identifiers assigned a variant named `"enabled"`; like the Env and TOML drivers, `enabled` is false. Gate A/B code on `variant`. |
| Database feature-flag splits | A `rullst_feature_flags` row whose `variants` column holds an A/B split now makes `DbFeatureDriver::enabled` (and therefore `feature::enabled` when the DB driver answers) false, as in the Env, TOML and Memory drivers. It was true when `rollout_percentage` was empty. `enabled_for` and `variant` are unchanged; gate A/B code on `variant`. |
| Security headers | Core and both Security header layers preserve an endpoint's exact `Referrer-Policy: no-referrer`, including when it occurs among duplicate values. Other endpoint values still yield to `SecureHeadersLayer` and `CspSecurityLayer`; the Core baseline now keeps them (see Core security header precedence). Review handlers that intentionally set this more restrictive policy. |
| Core WAF signatures | `waf_middleware`, which `Server` mounts in staging and production, now refuses injection structure instead of SQL and shell keywords. Ordinary text such as "Please select an option", "Delete my account" or "curl the API with your token" in a query, `Referer`, cookie or body is no longer rejected with 403. A quote followed by `or`/`and` and a comparison or by a SQL comment, a `;` followed by a SQL statement, `union [all] select`, SQL probe functions (`sleep(`, `waitfor delay`, `information_schema`…) and a shell metacharacter (`;`, `\|`, `&&`, a backtick, `$(`) followed by a command name are still refused, also when `/* */` comments separate keywords; XSS and traversal signatures are unchanged. JSON bodies are inspected key by key and string by string after decoding, so a `\u003c` escape no longer hides `<script` and JSON quotes no longer join a signature. The WAF remains a coarse baseline: keep parameterized SQL and shell-free process APIs. |
| Core security header precedence | `headers_middleware` (the staging and production baseline in `Server`) now adds each security header only when the response has none, so an explicit value from a handler or an inner layer (`Content-Security-Policy`, `X-Frame-Options`, HSTS, `Referrer-Policy`, `Permissions-Policy`, COOP, CORP, COEP, `X-XSS-Protection`) wins over the baseline instead of being replaced. When `rullst_security::SecureHeadersLayer` ran inside it, which now marks its responses with the new `rullst::security::SecurityHeadersApplied` extension, the baseline leaves all of those headers alone, so the headers its `SecureHeadersConfig` omits (`None`) stay absent. `Cache-Control: no-store` for responses without a cache policy and the shared `CspNonce` are unchanged. Review handlers and layers that set a weaker value (for example `Referrer-Policy: unsafe-url` or a CSP with `'unsafe-inline'`) and relied on the baseline to replace it. |
| AI provider streaming and stop reasons | `AnthropicProvider` and `GeminiProvider` now implement `StreamingAiProvider`, and their `capabilities()` report `streaming: true` and `explicit_cancellation: true`; code that chose a transport from those flags now streams them. Gemini's non-streaming `chat`/`prompt` now fail with `AiError::ApiError` when the candidate's `finishReason` is `MAX_TOKENS` or a safety-class reason (`SAFETY`, `RECITATION`, `LANGUAGE`, `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `IMAGE_SAFETY`) instead of returning the partial text, matching the Anthropic and OpenAI behaviour; raise the output limit or handle the error. The OpenAI-compatible stream (`OpenAiCompatibleProvider` with `with_streaming()`, used for OpenAI, DeepSeek, local servers and loopback Ollama) likewise fails with `AiError::ApiError` when a chunk reports `finish_reason` `length` or `content_filter` instead of completing with the text received so far. |
| AI image-beacon guardrail | The `data_exfiltration` check inspects every Markdown image even when the text contains no literal `http://` or `https://`: scheme-relative (`//host`), slash-less (`http:host`), backslash and reference-style beacons (with the definition anywhere in the text), unterminated destinations and labels containing a code span, raw HTML or an autolink that could hide a `]` (or a `<` followed by a bracket before the next `>`) are blocked; bracket-free constructs such as `Vec::<u8>` or `Box<dyn Fn()>` inside `vec![...]` no longer make a label ambiguous. It decodes CommonMark backslash escapes and entity or numeric character references in destinations, so `![x](https&#58;//host/c)` is blocked like the literal URL; an unrecognized named reference (for example `&eacute;`) makes that destination untrusted. Images and definitions inside code spans and closed fenced or indented code blocks are ignored, as CommonMark never renders them (code whose extent depends on an ambiguous layout is still read); lines end at LF, CRLF or a bare CR and only spaces and tabs make a line blank, so a bare CR or a no-break-space line can no longer turn a rendered image into apparent indented code. A reference image whose ASCII label matches no definition, such as `vec![x]` or `routes![...]` in Rust code, renders as literal text and is not blocked even next to a remote URL; a non-ASCII label, a label with a backslash-escaped bracket (read with its escapes, as `[a\]b]`) or an unterminated label is still blocked when the text names a remote URL, and a reference image whose definitions are all local is not blocked by an unrelated link. An inline image whose destination and title are not certainly valid (such as `![ß](x y)`) is also judged by the shortcut reference CommonMark falls back to, matched with Unicode case folding. |
| AI RAG tenant tags | `RagPipeline::answer` checks the tenant tag of every document the retriever returns, including those after the context budget is exhausted, and fails with `RagError::InvalidDocument` (audited as `ContextRejected`, no provider call) instead of answering when any of them belongs to another tenant. |
| Anthropic provider output | `AnthropicProvider` requests up to 16,000 output tokens instead of a fixed 1,024, and a reply whose `stop_reason` is `max_tokens`, `model_context_window_exceeded` or `refusal` now fails with `AiError::ApiError` instead of returning the partial text as a complete answer (so `StatefulChat` does not store it and `RagPipeline` audits `GenerationFailed`). Choose another limit with the new `with_max_tokens`; a longer reply can take longer than the 30-second default request deadline, so raise it with `with_request_timeout`. |
| OpenAI provider output | `OpenAiProvider` vision requests no longer send `max_tokens: 1024` (deprecated by OpenAI and rejected by reasoning models); like text requests they leave the output limit to the model. A chat, vision, JSON or structured-output reply whose `finish_reason` is `length` or `content_filter` now fails with `AiError::ApiError` instead of returning the partial text. DeepSeek and `OpenAiCompatibleProvider` are unchanged. |
| Ollama host | `OllamaProvider::new` (`OpenAiCompatibleProvider::ollama` since 13.0.0-alpha.5) and `AiClient::auto()` read `OLLAMA_HOST` the way Ollama does: a scheme-less value such as `127.0.0.1:11434`, `localhost` or `[::1]` now means `http` with port 11434 unless a valid port is named (`ollama.com` alone means `https://ollama.com:443`), instead of producing a URL every request rejected. Values with `http://` or `https://` are used as before. |
| AI chat memory keys on MySQL/MariaDB | `SqlChatMemory` tenant and conversation IDs compare case-sensitively on every backend; new MySQL/MariaDB tables use `ascii_bin` key columns, and `prepare_schema` never alters an existing table. On a table created by 12.x, an ID that differs from a stored one only by letter case fails closed (`ChatMemoryError::InvalidConfiguration`, `ConversationNotFound` or `RevisionConflict`). Stop chat-memory writers, back up both tables, review conversations that 12.x may have merged and apply the migration in the [AI README](https://github.com/Rullst/Rullst/blob/main/rullst-ai/README.md#upgrading-mysqlmariadb-chat-memory-tables). PostgreSQL and SQLite tables are unchanged. |
| Core CSRF on HEAD | `csrf_middleware` handles `HEAD` like `GET`: it installs the request-scoped `CsrfToken` and, when the request carries no CSRF cookie, sends the same `Set-Cookie` that GET would. A `get` route that extracts `Extension<CsrfToken>` now answers HEAD (monitors, crawlers, `curl -I`) with its GET status instead of 500. |
| Hot-reload machine endpoints | `Server::new_hot(...).with_machine_endpoints(policy)` now authenticates the policy's exact routes in the development hot-reload server, as the static server already did in every environment. Previously hot reload ignored the policy and those routes ran unauthenticated; development machine clients must now send the configured credentials. |
| Core JSON PII masking | With `enable_pii_masking`, JSON string escapes are decoded before masking, so `\uXXXX` hex digits never join a card-number run (which produced invalid JSON such as `\u****`), while escaped digits and `@` are masked like their literal characters. A masked character is written as a literal `*`; unmasked escapes keep their original spelling. |
| Core PII masking of range responses | With `enable_pii_masking`, a `206 Partial Content` response whose range would be masked now becomes `502` with `Cache-Control: no-store` instead of a rewritten 206 that kept its status but lost `Content-Range`. A range that needs no masking passes through unchanged. A `multipart/byteranges` response, previously passed through uninspected, is now checked part by part and withheld the same way when a textual part would be masked or when the body cannot be split exactly (invalid boundary or delimiter line, more than 256 parts, a part header block over 8 KiB, no close delimiter). |
| Security DLP, RASP and honeypot | `DlpResponseLayer` now also masks XML (`application/xml`, `+xml`), YAML and `application/javascript` responses, as it already did for text and JSON; review clients that compare such bodies byte for byte. A `206 Partial Content` response whose range contains a masked secret now becomes `502` with `Cache-Control: no-store` instead of a rewritten 206 without `Content-Range`. ### `html!` returns `Markup`

`cargo rullst upgrade` reports `V13-HTML-MARKUP-RETURN` for a function that
declares a `String` (`String`, `Html<String>`, `Result<String, _>`) and
returns `html!`, and `V13-HTML-RAW-MARKUP` for `RawHtml` around `html!`
output. Before:

```rust,ignore
use rullst::html;
use rullst::html::RawHtml;

fn badge(label: &str) -> String {
    html! { <span class="badge">{label}</span> }
}

fn rows(names: &[&str]) -> String {
    let rows: String = names
        .iter()
        .map(|name| html! { <tr><td>{name}</td><td>{RawHtml(badge("new"))}</td></tr> })
        .collect();
    html! { <table>{RawHtml(rows)}</table> }
}
```

After:

```rust
use rullst::html;
use rullst::html::Markup;

fn badge(label: &str) -> Markup {
    html! { <span class="badge">{label}</span> }
}

fn rows(names: &[&str]) -> Markup {
    let rows: Markup = names
        .iter()
        .map(|name| html! { <tr><td>{name}</td><td>{badge("new")}</td></tr> })
        .collect();
    html! { <table>{rows}</table> }
}

assert_eq!(
    rows(&["<Ana>"]),
    "<table><tr><td>&lt;Ana&gt;</td><td><span class=\"badge\">new</span></td></tr></table>"
);
```

Keep `RawHtml` (or `Markup::from_trusted`) only for trusted HTML produced
outside `html!`, such as a sanitizer's output, and never for request data.

### Moving off `chrono`

RustSec published
[RUSTSEC-2026-0543](https://rustsec.org/advisories/RUSTSEC-2026-0543.html)
on 2026-11-17: `chrono` is unmaintained. The advisory reports no
vulnerability, and the `chrono` maintainer recommends `jiff` or `time`. Up to
13.0.0-alpha.5 `chrono` 0.4 was a public dependency of Rullst 13, so
13.0.0-alpha.6 removes it from every Rullst crate and uses
[`jiff`](https://docs.rs/jiff/1) 1 instead. This section details the
"`chrono` replaced by `jiff`" row. Your application may keep using `chrono`
in its own code: declare it in your own `Cargo.toml` and convert values where
they reach a Rullst API.

**Database columns.** SQLx 0.9 has date/time codecs only for `chrono` and
`time`, and Rust's orphan rule prevents Rullst from implementing SQLx's traits
for jiff's types. The ORM therefore owns four column types in
`rullst_orm::temporal`, also exported as `rullst::orm::*` and `rullst::db::*`:

| `chrono` type (to alpha.5) | Rullst type (from alpha.6) | Wraps | Schema helper |
| :--- | :--- | :--- | :--- |
| `DateTime<Utc>` | `rullst::orm::Timestamp` | `jiff::Timestamp` | `timestamp_tz()`, and `timestamps()` |
| `NaiveDateTime` | `rullst::orm::DateTime` | `jiff::civil::DateTime` | `timestamp()` |
| `NaiveDate` | `rullst::orm::Date` | `jiff::civil::Date` | `date()` |
| `NaiveTime` | `rullst::orm::Time` | `jiff::civil::Time` | `time()` |

Each type converts to and from the jiff type with `From` and dereferences to
it, so jiff's methods apply (`at.as_second()`). The ORM types also have
their own arithmetic and accessors, which take ORM values and return an ORM
value where the result is a date or a time: `checked_add`, `checked_sub`,
`saturating_add`, `saturating_sub`, `duration_since` and `duration_until` on
`Timestamp`, `DateTime` and `Date`; `tomorrow` and `yesterday` on `DateTime`
and `Date`; `days_since` and `days_until` on `Date`; and `date()` and `time()`
on `DateTime`. Do not convert to jiff and back for these: an `.into()` on
their result turns an ORM value into itself, which clippy reports as
`useless_conversion`. Convert with `.into()` only what jiff's own methods
return. `Display`, `Debug`, serde and `FromStr` are byte for byte those of
the `chrono` type it replaces (a `Timestamp` displays
as `2026-10-15 09:30:00.500 UTC` and serializes as
`"2026-10-15T09:30:00.500Z"`), and parsing accepts every form `chrono`
accepted first, then jiff's own forms (`FromStr::Err` is `jiff::Error`). The
jiff value behind `Deref` formats in jiff's style
(`2026-10-15T09:30:00.5Z`). The types are also `Copy`, `Ord` and `Hash`, and
`Timestamp::now()` reads the system clock. `rullst::orm::chrono`
(`rullst_orm::chrono`) is removed, and `rullst::orm::jiff` re-exports the jiff
crate that these types use. Step 20 of the
[alpha.5 to alpha.6 checklist](#upgrading-an-alpha5-application-to-alpha6)
maps chrono's methods to jiff's (`format` to `strftime`, `parse_from_str` to
`strptime`, `timestamp` to `as_second`, …). Use the new types in model fields (also inside
`Option`), in `#[derive(Nexus)]` models and as query values. In
`RullstValue`, the variants `Timestamp`, `CivilDateTime`, `CivilDate` and
`CivilTime` replace `DateTime`, `NaiveDateTime`, `Date` and `Time`. Your own
SQLx queries can bind and read the new types on the strict pools; the SQLx
`Any` pool has no codec for them, as it had none for `chrono`. If your own
SQLx code binds or reads `chrono` values (or names `sqlx::types::chrono`),
enable the `chrono` feature on your own `sqlx` dependency, because Rullst no
longer enables it. `rullst::db::*` glob-exports `DateTime`, `Date`, `Time` and
`Timestamp`, so a module that also has `use chrono::prelude::*` gets
ambiguous names: import the types it uses by name.

**Stored data needs no migration.** On SQLite, PostgreSQL, MySQL and MariaDB
the new types write exactly the bytes that the `chrono` types wrote, and they
read every form those types read. Existing rows need no data migration, and
old and new rows can share a column. `Default` gives the same values as
before: 1970-01-01 for `Date`, 1970-01-01T00:00:00 for `DateTime`, the Unix
epoch for `Timestamp` and midnight for `Time`.

jiff's range is narrower than `chrono`'s. A value outside it is a decode or
parse error, never a panic or a clamped value:

- `DateTime`, `Date` and `Time` hold years -9999 to 9999.
- `Timestamp` holds `-9999-01-02T01:59:59Z..=9999-12-30T22:00:00.999999999Z`.
  The common end-of-time sentinel `9999-12-31 23:59:59` in a `timestamp_tz()`
  column no longer reads: the error names the range and suggests NULL in an
  `Option<Timestamp>` field for "no end", a value within the range, or reading
  the column as a civil `DateTime`, which keeps the full range. Find such
  rows before upgrading:
  `SELECT id FROM events WHERE ends_at > '9999-12-30 22:00:00+00'` on
  PostgreSQL, or `> '9999-12-30 22:00:00'` on MySQL/MariaDB.

A few stored values read differently; none of them is a value Rullst writes:

- a leap second (`:60`) reads as second 59, with the same fraction;
- a few lenient text forms that only `chrono` read from a stored timestamp,
  such as a space before the offset or a `UTC` suffix, no longer decode;
- a Nexus date-time whose UTC instant falls in the year 10000 may fail on the
  strict PostgreSQL or MySQL/MariaDB pools.

**APIs outside the database take jiff's own types:**

- **Core.** `Locale::format_date(date: impl Into<jiff::civil::Date>, style)`,
  `format_time(time: impl Into<jiff::civil::Time>, style)` and
  `format_datetime(value: impl Into<jiff::civil::DateTime>, date_style,
  time_style)` used to take `&impl chrono::Datelike` and `Timelike`. Pass a
  civil value by value: an ORM `Date`, `Time` or `DateTime` converts as it
  is, and `*value` turns an ORM `DateTime` into the civil date-time that
  `format_date` and `format_time` also accept. Each also accepts a
  `&jiff::ZonedDateTime`, so for an instant pass
  `&jiff::ZonedDateTime` in the reader's zone
  (`at.in_tz("America/Sao_Paulo")?`); looking a zone up by name needs jiff's
  time zone database, which `jiff = "1"` with its default features in your
  own `Cargo.toml` provides. The formatted text is unchanged. Every
  Core build now depends on `jiff`. The scheduler's API is unchanged, and the
  `scheduler-tz` feature still adds the IANA time zone database.
- **Mail.** `Message.send_at` is an `Option<jiff::Timestamp>`, and
  `Message::send_at(timestamp: impl Into<jiff::Timestamp>)` and the memory
  driver's assertion `MailAssertion::with_scheduled_at(expected: impl
  Into<jiff::Timestamp>)` take one. The `expires_at` field of
  `AccountEvent::PasswordResetAt` and `AccountEvent::EmailLoginAt` is also a
  `jiff::Timestamp`.
- **Capital.** `Invoice.date` is a `jiff::Timestamp`, and
  `Invoice::new(invoice_id, customer_email, date: impl
  Into<jiff::Timestamp>, currency)`.
- An ORM `Timestamp` passes to these methods as it is; assign one to the
  fields with `.into()`.
- Messaging, Security and Auth have no public change. The serialized forms
  do not change: messages queued as JSON before the upgrade deliver at their
  time, and an invoice's JSON is byte for byte the same.

**Typical rewrites.** In the right column, `Timestamp`, `SignedDuration` and
`at` are jiff's types. An ORM `Timestamp` dereferences to `jiff::Timestamp`,
so write `*at` where an expression needs the jiff value itself.

| To alpha.5 (`chrono`) | From alpha.6 (`jiff`) |
| :--- | :--- |
| `Utc::now()` | `jiff::Timestamp::now()`, or `rullst::orm::Timestamp::now()` for a model field |
| `Utc::now() + Duration::minutes(5)` | `Timestamp::now() + SignedDuration::from_mins(5)`, or `Timestamp::now().checked_add(SignedDuration::from_mins(5))?`, which returns an error instead of panicking at the end of jiff's range |
| `at.timestamp()` | `at.as_second()` |
| `NaiveDate::from_ymd_opt(2026, 10, 22)` | `jiff::civil::Date::new(2026, 10, 22)?` (or `jiff::civil::date(2026, 10, 22)` for a constant) |
| `"2026-10-15T09:30:00Z".parse::<DateTime<Utc>>()` | `"2026-10-15T09:30:00Z".parse::<Timestamp>()` |
| `at.format("%d/%m/%Y")` | `at.strftime("%d/%m/%Y")` |
| `at.naive_utc()` | `jiff::tz::TimeZone::UTC.to_datetime(at)` |

```rust
use rullst::orm::jiff::{civil, SignedDuration, ToSpan};
use rullst::orm::{Date, DateTime, Timestamp};

// A `timestamp_tz()` field and an instant five minutes later.
let created_at = Timestamp::now();
let expires_at = created_at.checked_add(SignedDuration::from_mins(5))?;
assert_eq!(expires_at.as_second() - created_at.as_second(), 300);

// `Display` keeps chrono's text; the jiff value behind `Deref` has jiff's.
let at: Timestamp = "2026-10-15T09:30:00.5Z".parse()?;
assert_eq!(at.to_string(), "2026-10-15 09:30:00.500 UTC");
assert_eq!((*at).to_string(), "2026-10-15T09:30:00.5Z");

// A `date()` field. Mail and Capital take an ORM `Timestamp` or a jiff one.
let due: Date = civil::Date::new(2026, 10, 22)?.into();
assert_eq!(due.to_string(), "2026-10-22");
let invoice = rullst::capital::Invoice::new("INV-1", "ana@example.com", created_at, "BRL");
let reminder = rullst::mail::Message::new().send_at(expires_at);

// Arithmetic on an ORM value returns an ORM value: no `.into()` round trip.
let class_at: DateTime = "2026-10-15T18:30:00".parse()?;
let reminder_at: DateTime = class_at.checked_sub(2.hours())?;
let next_week: Date = class_at.date().saturating_add(7.days());
assert_eq!(next_week.days_since(class_at.date()), 7);
assert_eq!(reminder_at.duration_until(class_at), SignedDuration::from_hours(2));

// Compare like with like: `*` gives the jiff value behind an ORM value.
let doors_open: civil::DateTime = civil::date(2026, 10, 15).at(18, 0, 0, 0);
assert!(*class_at > doors_open);
assert!(class_at > DateTime::from(doors_open));
# let _ = (invoice, reminder);
# Ok::<(), Box<dyn std::error::Error>>(())
```

**`DateTime` and `DateTime`.** `rullst::orm::DateTime` and
`jiff::civil::DateTime` are different types with the same name, and so are the
other three pairs. A comparison or an argument that mixes them fails with
E0308 "mismatched types", whose note says that the two types "have similar
names, but are actually distinct types". It usually comes from a `*` in front
of an ORM value compared with a value an ORM method returned, as in
`*class_at <= now.saturating_add(1.hours())` where `now` is an ORM
`DateTime`. Compare like with like: drop the `*` there, dereference the ORM
side when the other side is jiff's (`*class_at > doors_open`), or convert the
jiff side (`class_at > DateTime::from(doors_open)`).

**How `cargo rullst upgrade` helps.** Four `MUST-CHANGE` rules, all
introduced in 13.0.0-alpha.6, report the code that passes or reads `chrono`
values where Rullst now takes the new types. Each one names the "`chrono`
replaced by `jiff`" row and the replacement to apply by hand:

- `V13-ORM-CHRONO-TYPES`: `chrono` types in model fields, Nexus models and
  query values, and `rullst::orm::chrono` paths;
- `V13-LOCALE-JIFF-DATES`: `Locale::format_date`, `format_time` and
  `format_datetime` calls;
- `V13-MAIL-JIFF-TIMESTAMPS`: `Message::send_at`, `with_scheduled_at` and the
  `expires_at` of the account events;
- `V13-CAPITAL-INVOICE-JIFF-DATE`: `Invoice::new` and `invoice.date`.

### Messaging schedules and POSIX cron

The `cron` crate depends on `chrono`, so 13.0.0-alpha.6 also stops using it
for Messaging's durable recurring publications (`schedules-postgres`, facade
`messaging-schedules-postgres`); see the "Messaging schedules use the
scheduler's cron syntax" row. A new `RecurringDefinition` now reads its five
fields exactly like [Core's `Scheduler::task`](crates/core.md), with POSIX
semantics in UTC:

| | Up to alpha.5 (the `cron` crate) | From alpha.6 (POSIX, like `Scheduler::task`) |
| :--- | :--- | :--- |
| Weekday numbers | 1 = Sunday to 7 = Saturday; 0 is rejected | 0 to 7: 0 and 7 are Sunday, 1 is Monday |
| Day-of-month and weekday both restricted | both must match | either one matches |
| A field that starts or ends with `,`, `-` or `/` | joined with its neighbour, which shifts the later fields | rejected |

Weekday names (`Mon`, `Mon-Fri`) mean the same day in both syntaxes. The same
text can change meaning, as these examples show:

| Expression | Up to alpha.5 | From alpha.6 |
| :--- | :--- | :--- |
| `0 9 * * 1` | Sundays at 09:00 | Mondays at 09:00 |
| `0 9 * * 2-6` | Monday to Friday | Tuesday to Saturday |
| `0 9 * * 7` | Saturdays | Sundays |
| `0 9 * * 0` | rejected | Sundays |
| `0 0 1 * Mon` | the 1st, when it is a Monday | the 1st of every month, and every Monday |
| `1, 2 * * *` | accepted, with `1,` and `2` joined into one field | rejected by `RecurringDefinition::new` |

Definitions stored before the upgrade keep their meaning. Each definition
records the syntax it was created with, and a definition stored without that
record is read with the earlier `cron`-crate rules, now called the legacy
syntax. `RecurringDefinition::syntax()` and `RecurringMetadata::syntax()`
return `CronSyntax::Posix` or `CronSyntax::Legacy`
(`rullst::messaging::schedules::CronSyntax`, `#[non_exhaustive]`), and
`create` and `schedules()` return the metadata, so inspection lists show
which definitions are legacy. The legacy syntax is deprecated: reading such
definitions is planned for removal in 14.0. An expression that only the
legacy syntax accepted, such as `1, 2 * * *`, is refused by
`RecurringDefinition::new` with its own `InvalidInput` message, while a stored
definition with it keeps running. A legacy definition deserialized from JSON
exported before the upgrade keeps its syntax, and `create` accepts it, so an
export and import moves schedules without changing their meaning.
`RecurringDefinition::posix_equivalent()` returns the POSIX expression whose
occurrences are exactly those of a definition (`0 9 * * 1`, Sundays in the
legacy syntax, gives `0 9 * * 0`), or `None` when there is none: both day
fields restricted, tokens that joined into another field, or a result over 128
bytes. A POSIX definition returns its own expression.

`cargo rullst upgrade` reports `V13-MESSAGING-CRON-POSIX` at each
`RecurringDefinition::new` call whose expression is not a string literal that
means the same in both syntaxes, and gives a literal's POSIX form when the
rewrite is mechanical. What to do depends on whether that schedule is already
stored:

- **A schedule already stored** (created before the upgrade). Calling
  `create` again at startup with the same name and the same expression
  replays: it returns the stored metadata with `syntax() ==
  CronSyntax::Legacy`, logs a warning and keeps the old meaning (`0 9 * * 1`
  stays Sundays), so startup does not fail. Leave the code as it is to keep
  the legacy schedule until 14.0. To move it to POSIX, cancel it and create
  the POSIX expression (`posix_equivalent()` of the stored definition, when it
  has one) under a new name. Any other definition under a legacy name, the
  rewritten expression included (`0 9 * * 0`), fails with
  `RecurringError::LegacyDefinition`: "schedule name is held by a legacy cron
  definition; keep its expression to keep it running, or cancel it and create
  the POSIX definition under a new name". A cancelled name can never be
  reused.
- **A new schedule.** Write the expression in the POSIX syntax: subtract one
  from each weekday number, or use weekday names, and where an expression
  restricts both the day of the month and the weekday, decide whether you
  mean "both" or "either".

Check expressions read from configuration or a database yourself. Plan a
rollback as a database restore: a 13.0 prerelease before alpha.6 cannot read
definitions that record their syntax, so take a backup before alpha.6 creates
its first definition.

## Upgrading an alpha.2 application to alpha.3

This checklist moves an application from 13.0.0-alpha.2 to 13.0.0-alpha.3.
The rows above that name alpha.3, and the ORM database-managed columns, ORM
dirty tracking and Omni rows, are the changes in between. The
[rehearsal on generated starters](tutorials/36-assisted-framework-upgrades.md#1300-alpha2-to-1300-alpha3)
shows the expected result.

1. **Prepare.** Work on a branch with a clean tree and a committed
   `Cargo.lock`, record the current `cargo test` result, and back up every
   database (check that the backup restores).
2. **Install the alpha.3 CLI.**
   `cargo install cargo-rullst --version =13.0.0-alpha.3 --locked --force`,
   then `rullst --version` must print `13.0.0-alpha.3`.
3. **Name the features.** `rullst` (which enabled `orm`, `drivers-all` and
   `queue-sqlite`) and `rullst-orm` (`drivers-all`) have no default features
   any more. A dependency that relied on them lists what the application
   uses, for example
   `rullst = { version = "=13.0.0-alpha.3", default-features = false, features = ["orm", "strict-sqlite", "queue-sqlite"] }`
   (`drivers-all` keeps the three SQLx drivers). Remove `offline-sync` from
   `rullst` and `rullst-core` features. Projects generated by `cargo rullst
   new` already disable the defaults and list their features.
4. **Inspect.** Run `cargo rullst upgrade --dry-run` and fix every
   `MUST-CHANGE` finding first (`V13-OFFLINE-SYNC-REMOVED` is the one alpha.3
   adds). These findings concern alpha.3 changes and usually need an edit:
   - `V13-ORM-SKIP-MANAGED-COLUMNS`: replace `#[orm(skip)]` with
     `#[orm(db_default)]` on `User::is_admin` and `User::session_epoch` (SaaS,
     LMS and `cargo rullst auth` models generated by alpha.2) and on any
     other column the database manages. No schema change is needed.
   - `V13-ORM-TRANSACTION-ERRORS`: `Orm::transaction` returns its closure's
     own error type, so match that error instead of `DatabaseError`. A
     closure whose error type lacks `From<rullst_orm::Error>` (such as
     `String`) no longer compiles, which `cargo check` reports; return
     `rullst_orm::Error` or an application error that wraps it.
   - `V13-RULLST-DEFAULT-FEATURES` and `V13-ORM-DEFAULT-FEATURES`: step 3.
   - `V13-CONNECT-GITHUB-EMAIL`: the GitHub provider now returns the primary
     address and GitHub's verified flag; link or create accounts on it only
     when `email_verified == Some(true)`.
   - `V13-OMNI-REMOVED` and `V13-OFFLINE-SYNC-REMOVED`: replace the Omni
     shell with `cargo rullst make:pwa`, as the Omni row describes.

   The plan reads the application's version from its manifests and
   `Cargo.lock` and applies only the rules introduced after 13.0.0-alpha.2,
   which are the ones above; its `Rules:` line says how many earlier rules it
   skipped. If it names 13.0.0-alpha.1 instead, a requirement still has the
   caret form of the alpha.1 CLI (`"13.0.0-alpha.1"`), and the alpha.2 rules
   are listed too. `--all-rules` also lists the rules for the 12.x to 13
   changes that alpha.2 already contained, such as `V13-REFERRER-NO-REFERRER`,
   `V13-MAIL-FACADE-CONFIG`, `V13-LMS-RECORD-PROGRESS` and
   `V13-HOT-RELOAD-MACHINE-ENDPOINTS`; an alpha.2 application already runs
   with those changes, so they need no edit for this step.
5. **Apply.** `cargo rullst upgrade` pins every Rullst dependency, including
   direct `rullst-auth`, `rullst-security` or `rullst-connect` lines, to
   `=13.0.0-alpha.3`, runs `cargo fix` and `cargo check --locked`, and
   restores the files if a step fails (`--keep-on-failure` keeps the failed
   state for diagnosis). Make the edits from step 4, then update the
   dependencies of the changelog's Dependency security entries that the
   lockfile contains:
   `cargo update -p ammonia -p rustls-webpki -p webpki-roots -p webpki-root-certs`.
6. **Read the alpha.3 rows that no rule locates** and adjust the application
   where it depends on them: ORM transactional migrations and the pool (no
   `Orm::pool()` inside a `within_transaction()` migration), Connect mock
   credentials and Connect mock authorization URL (mock credentials need the
   `mock` feature, `oauth-mock` on the facade), Production log defaults
   (health probes are no longer logged, SQLx INFO events are hidden, and an
   invalid `RULLST_LOG_HEALTH_PROBES` stops startup), and the opt-in ORM
   dirty tracking, Nexus time zone (`Nexus::with_time_zone`, in the Nexus
   dates and times row) and Account mail language and product name. Workarounds
   for alpha.2 defects that the changelog's "Fixes from alpha.2 dogfooding"
   lists, such as raw SQL to filter on `is_admin`, can then go.
7. **Verify** with the production feature set: `cargo build`, `cargo test`
   and `cargo clippy --all-targets -- -D warnings`; `db:migrate` against a
   restored copy of the production database; then sign-in, "Sign out
   everywhere", Nexus access for an `is_admin` account, each configured
   provider and the health probes on staging before production.

## Upgrading an alpha.3 application to alpha.4

This checklist moves an application from 13.0.0-alpha.3 to 13.0.0-alpha.4.
The rows above that name alpha.4 are the changes in between. Most of them
change the CLI and the files it generates. In the framework crates,
`#[derive(Orm)]` now implements `FromRow` and Rullst no longer enables SQLx's
macros, the facade's `nexus` feature leaves out the AI assistant, every TLS
connection uses aws-lc-rs, and some internals are hidden from the API
documentation. Work through the steps in order.

1. **Prepare.** Work on a branch with a clean tree and a committed
   `Cargo.lock`, record the current `cargo test` result, and back up every
   database (check that the backup restores).
2. **Install the alpha.4 CLI.**
   `cargo install cargo-rullst --version =13.0.0-alpha.4 --locked --force`,
   then `rullst --version` must print `13.0.0-alpha.4`. `cargo rullst green`
   (the former `footprint`) is part of this package; there is nothing else to
   install. `cargo rullst ai` was removed: use your editor's or terminal's AI
   assistant with the project's `AGENTS.md` (`cargo rullst generate:ai-context`)
   and the published [`llms.txt`](https://rullst.github.io/Rullst/llms.txt).
3. **Inspect.** `cargo rullst upgrade --dry-run` applies only the rules
   introduced after 13.0.0-alpha.3. These eight can appear:
   - `V13-ORM-FROM-ROW` (`MUST-CHANGE`, step 5): a model that derives
     `FromRow` beside `Orm`. Every model generated before alpha.4 does
     (`#[derive(Debug, Clone, FromRow, Orm)]`).
   - `V13-SQLX-MACROS` (`MUST-CHANGE`, step 5): a SQLx derive on a struct or
     enum that is not a model, or a `sqlx::query!`-style macro, while no
     manifest enables SQLx's `derive` or `macros` feature.
   - `V13-SQLX-TLS-RING` (`REVIEW`, step 6): a `sqlx` dependency or a
     `[features]` entry that enables `tls-rustls`, `tls-rustls-ring` or
     `tls-rustls-ring-webpki`. Projects generated before alpha.4 list
     `tls-rustls`.
   - `V13-NEXUS-AI-FEATURE` (`REVIEW`, step 7): a `rullst` dependency with
     `nexus` or `nexus-tz` but not `nexus-ai`, or a `rullst-nexus` dependency
     without default features and without `ai`.
   - `V13-CLI-AI-REMOVED`, `V13-CLI-SELF-UPDATE-REMOVED`,
     `V13-DEPLOY-TARGETS-REMOVED` and `V13-DEPLOY-GENERATORS-REMOVED`
     (`REVIEW`, step 9): scripts that run removed commands, and the files of
     the removed deploy targets and generators.

   The 13.0.0-alpha.5 CLI adds five rules for alpha.4 changes that the
   alpha.4 CLI does not locate: `V13-SQLX-TLS-NATIVE-ROOTS` (step 6),
   `V13-CLI-MIGRATION-AUTO-STATUS` and `V13-CLI-BLUEPRINTS-REMOVED` (step 9),
   and `V13-DEPLOY-SQLITE-URL` and `V13-DEPLOY-CADDY-HEALTH` (step 10).
   Steps 9 to 11 also list changes that no rule locates; read them even when
   the plan has no finding.
4. **Apply, keeping a failed state.** A model that still derives `FromRow`
   does not compile against alpha.4, and one without it does not compile
   against alpha.3, so the edits of step 5 come after the version change. Run
   `cargo rullst upgrade --keep-on-failure`: it pins every Rullst dependency
   to `=13.0.0-alpha.4`, runs `cargo fix` and `cargo check --locked`, and,
   when they fail, keeps the edited files instead of restoring them and names
   the must-change findings. When the plan has no `MUST-CHANGE` finding, a
   plain `cargo rullst upgrade` is enough; go on with step 6. From the
   13.0.0-alpha.5 CLI, a plain `cargo rullst upgrade` stops before changing
   anything while the plan has must-change findings, so `--keep-on-failure`
   is how it applies the versions first.
5. **Fix the models and SQLx macros.**
   - Remove `FromRow` from each model's derive list and from the `use` line
     that imports it: `#[derive(Debug, Clone, FromRow, Orm)]` becomes
     `#[derive(Debug, Clone, Orm)]`, and `use rullst::db::{Orm, FromRow, RowSnapshot};`
     becomes `use rullst::db::{Orm, RowSnapshot};`. A model that keeps its
     own `FromRow` (hand-written, or SQLx's derive) declares
     `#[orm(custom_from_row)]` instead.
   - For SQLx derives on other types (`FromRow`, `Type`, `Encode`, `Decode`)
     and `sqlx::query!`-style macros, add `derive` or `macros` to the features
     of the application's own `sqlx` dependency. This compiles `sqlx-macros`
     again ([Build times](build-times.md)).
6. **Switch SQLx to aws-lc-rs.** In the application's `sqlx` dependency and
   in any `[features]` entry, replace `tls-rustls` (or `tls-rustls-ring`,
   `tls-rustls-ring-webpki`) with `tls-rustls-aws-lc-rs`. SQLx prefers ring
   whenever any crate enables it, so one such feature keeps every database
   connection on ring while Rullst's other TLS connections use aws-lc-rs. Keep
   the `sqlx` dependency itself: the CLI reads it to recognise a SQLx project.
   The alpha.4 CLI does not report `tls-rustls-ring-native-roots` (the alpha.5
   CLI reviews it as `V13-SQLX-TLS-NATIVE-ROOTS`), because switching it
   changes the trusted roots: SQLx 0.9 has no aws-lc-rs feature with the
   operating system's roots, and `tls-rustls-aws-lc-rs` trusts the bundled
   WebPKI roots. Switch, passing a private CA with the connection's
   `sslrootcert` or `ssl-ca` option, or keep it and record why (TLS crypto
   provider row,
   [cryptography providers](security-architecture.md#cryptography-providers)).
7. **Decide on the Nexus AI assistant.** If the application uses
   `/nexus/chat`, add `nexus-ai` to the `rullst` features (or `ai` to a
   `rullst-nexus` dependency without default features). Otherwise nothing is
   needed: both chat routes answer `404 Not Found` with a notice, the panel
   shows no assistant link, and Nexus no longer brings `rullst-ai` into the
   build.
8. **Validate.** Run `cargo rullst upgrade` again. It makes no further version
   edits and checks the result with `cargo fix` and `cargo check --locked`.
9. **Update scripts, CI and other tools.** Replace the commands the review
   rules name:
   - `rullst ai …` with your own assistant, and `rullst footprint` with
     `rullst green` (`V13-CLI-AI-REMOVED`); on alpha.5 the command is
     `footprint` again (see the next checklist);
   - `update check|verify|stage|install` and `update guided --scope|--root`
     with `cargo install cargo-rullst --version =<version> --locked`, keeping
     `update project …` (`V13-CLI-SELF-UPDATE-REMOVED`);
   - `deploy --platform fly|railway|render`, `foundry:init`,
     `foundry:deploy`, `nixify`, `generate:buildah` and `make:grpc`
     (`V13-DEPLOY-TARGETS-REMOVED`, `V13-DEPLOY-GENERATORS-REMOVED`). The
     files they generated (`fly.toml`, `render.yaml`, `railway.json`,
     `Foundry.toml`, a `nixify` `flake.nix`, `build_buildah.sh`,
     `src/grpc/mod.rs`) stay yours and keep working with their own tools; keep
     or delete them.

   The alpha.4 CLI locates none of these (the alpha.5 CLI reports the first two,
   as `V13-CLI-BLUEPRINTS-REMOVED` and `V13-CLI-MIGRATION-AUTO-STATUS`);
   check them yourself:
   - `cargo rullst new --blueprint lms|blog|portfolio|erp` fails before
     writing anything: copy the application from [`examples/`](examples.md)
     instead;
   - `cargo rullst make:migration:auto` exits with status 1 when there is no
     SQLite database to compare (no `.env`, no `DATABASE_URL`, a non-SQLite
     URL or a Turso primary);
   - a client of the retired `POST /_rullst/autofix` reads `context_url`
     instead of `command`.
10. **Regenerate the deployment files.** An application deployed with the
    files of `cargo rullst deploy --platform vps` or `cargo rullst dockerize`
    runs `cargo rullst deploy` again. It keeps an existing `Dockerfile` and
    `Caddyfile` and writes `compose.yaml`, which replaces
    `docker-compose.prod.yml` (that file stays until you remove it). Then:
    - for SQLite, `deploy` warns when the `Dockerfile` lacks
      `ENV DATABASE_URL=sqlite:///app/data/rullst.db?mode=rwc`. Add it to the
      last stage, or set `DATABASE_URL` in `.env.production`; otherwise the
      database path points into the image's read-only `/app` and the app stops
      at startup;
    - the new `Caddyfile` checks `/health` every 5 seconds and holds requests
      for up to 15 seconds (`lb_try_duration`) while the app restarts. To get
      it, move the old file aside and run `cargo rullst deploy` again, or copy
      its `reverse_proxy` block;
    - since 13.0.0-alpha.5 the generated `Dockerfile` has a `static-assets`
      stage that writes the `.br`/`.zst` siblings of `static/`, which the
      runtime stage copies. A Dockerfile generated earlier serves static
      files uncompressed unless `cargo rullst build` ran before
      `docker build`: copy the stage from a Dockerfile that
      `cargo rullst dockerize` writes in a scratch copy of the project. No
      `upgrade` rule reports it. In alpha.5 pages stayed uncompressed: the
      `Caddyfile` had no `encode` for them because they carried the CSRF
      token unmasked. Since 13.0.0-alpha.6 the token is masked per response
      and the generated `Caddyfile` compresses pages; see "Compressed pages
      in the generated Caddyfile" and
      [Compression](vm-deployment.md#6-start-it).

    The alpha.4 CLI reports neither file (the alpha.5 CLI reports both, as
    `V13-DEPLOY-SQLITE-URL` and `V13-DEPLOY-CADDY-HEALTH`); start the stack as the
    [Linux VM guide](vm-deployment.md) shows.
11. **Optional clean-ups.** No rule reports these.
    - A `tracing` or `tokio` dependency declared only for `#[derive(Orm)]` can
      go (ORM derive dependencies row); keep it where your own code uses it.
      `tracing-subscriber` can go when no code uses `tracing_subscriber`.
    - A SaaS application whose code does not import `rullst_connect` can
      remove that dependency.
    - Copy the `[profile.dev]` sections that new projects get
      ([Build times](build-times.md)).
    - Code that names an item now hidden from the documentation keeps
      compiling; move to the replacement that the "Internals hidden from the
      API documentation" row names.
    - A `--no-database` project can delete its empty `rullst.db` and, with
      `--docker`, the Dockerfile's `DATABASE_URL` line.
    - If `Cargo.lock` has `crypto-bigint` 0.7.6 to 0.7.8, which crates.io
      yanked, run `cargo update -p crypto-bigint`.
12. **Verify** with the production feature set: `cargo build`, `cargo test`
    and `cargo clippy --all-targets -- -D warnings`; `db:migrate` against a
    restored copy of the production database; then, on staging, sign-in,
    Nexus (with or without the assistant), each configured provider and the
    health probes before production.

## Upgrading an alpha.5 application to alpha.6

This checklist moves an application from 13.0.0-alpha.5 to 13.0.0-alpha.6.
The rows above that name alpha.6 are the changes in between. alpha.6 is the
13.0 feature and public API freeze: it removes every API that was still
deprecated, makes the public enums and structs that can grow
`#[non_exhaustive]`, makes each ORM model choose what `save()` writes, puts
passkeys behind a feature, stops the health probes from reporting the
framework version, and changes the security baseline (CSRF and the secure headers in
every environment, a CSRF token masked per response, static files by path
and a CSP nonce only on HTML responses). It also keeps the OpenTelemetry
crates, utoipa and the `validator` error type out of the public API,
replaces chrono with jiff in Rullst's date and time APIs, and reads
messaging schedules with the scheduler's cron syntax. The
access log is written by a
background thread, cron fields are checked one by one, and `cargo rullst
auth` sets up server-side login sessions. Each item below names the
`cargo rullst upgrade` rule that locates it, or says that no rule does.
Work through the steps in order.

1. **Prepare.** Work on a branch with a clean tree and a committed
   `Cargo.lock`, record the current `cargo test` result, and back up every
   database (check that the backup restores).
2. **Install the alpha.6 CLI.**
   `cargo install cargo-rullst --version =13.0.0-alpha.6 --locked --force`,
   then `rullst --version` must print `13.0.0-alpha.6`.
3. **Inspect.** `cargo rullst upgrade --dry-run` applies only the rules
   introduced after 13.0.0-alpha.5, and since alpha.6 it reports a rule at
   every line it matches, so expect more locations than an alpha.5 plan
   showed. If the manifests already pin `=13.0.0-alpha.6` (you switched the
   versions first), the plan applies none of these rules, because they are
   not newer than the version the project uses; run
   `cargo rullst upgrade --dry-run --from 13.0.0-alpha.5` (a CLI from
   13.0.0-rc.1 on warns about it and accepts `--from`; with the alpha.6 CLI,
   use `--all-rules`). These rules can appear:
   - `MUST-CHANGE`: `V13-MAIL-DEPRECATED-REMOVED`,
     `V13-SECURITY-DEPRECATED-REMOVED`, `V13-CONNECT-INFALLIBLE-NEW-REMOVED`,
     `V13-ROUTE-MARKER-REMOVED` and `V13-ORM-SCHEMA-DIFF-REMOVED` (step 5),
     `V13-ORM-SAVE-MODE` (step 6), `V13-AUTH-PASSKEYS-FEATURE` (step 7),
     `V13-HEALTH-PROBE-VERSION-FIELD` (step 8),
     `V13-MEDIA-PROCESSING-MATCH` (step 17), `V13-NON-EXHAUSTIVE-MATCH`
     and `V13-NON-EXHAUSTIVE-LITERAL` (step 18),
     `V13-TELEMETRY-LAYER-TYPE`, `V13-VALIDATION-FIELD-ERRORS` and
     `V13-STUDIO-OPENAPI-INFERRED` (step 19), `V13-ORM-CHRONO-TYPES`,
     `V13-LOCALE-JIFF-DATES`, `V13-MAIL-JIFF-TIMESTAMPS` and
     `V13-CAPITAL-INVOICE-JIFF-DATE` (step 20), and
     `V13-MESSAGING-CRON-POSIX` (step 21).
   - `REVIEW`: `V13-IOT-OTA-LEGACY-REMOVED`,
     `V13-NEXUS-INFALLIBLE-BUILD-REMOVED`, `V13-AI-DEPRECATED-REMOVED` and
     `V13-QUEUE-PURGE-COMPLETED-REMOVED` (step 5, review findings because
     another type can have a method of that name),
     `V13-HEALTH-FRAMEWORK-VERSION` (step 8), `V13-SCHEDULER-CRON-FIELDS`
     (step 9), `V13-ROUTER-BASELINE-LAYERS` (step 10),
     `V13-CSRF-STATIC-PREFIXES` (step 11), `V13-CSRF-COOKIE-IN-PAGE` and
     `V13-CSRF-TOKEN-COMPARED` (step 12), `V13-DEPLOY-CADDY-ENCODE` (step 15),
     `V13-NON-EXHAUSTIVE-LITERAL-GLOB` (step 18),
     `V13-AUTH-SESSION-REGISTRY` and `V13-AUTH-SESSION-EPOCH-CALLS` (step
     16), `V13-JSONWEBTOKEN-12` and
     `V13-ED25519-DALEK-3` (step 22), and `V13-SQLITE-WAL-AVAILABLE` (the
     optional WAL step at the end).

   The changes of steps 13 and 14 have no rule, and parts of steps 9, 10, 12
   and 22 have none: read them even when the plan is empty.
4. **Apply, keeping a failed state.** Code that uses the removed APIs, a
   model without a save mode, passkeys without the feature, or a `match` or
   struct literal of a type that became `#[non_exhaustive]` does not compile
   against alpha.6. Run `cargo rullst upgrade --keep-on-failure`: it pins
   every Rullst dependency to `=13.0.0-alpha.6`, runs `cargo fix` and
   `cargo check --locked`, and, when they fail, keeps the edited files and
   names the must-change findings. Fix what steps 5 to 8 and 17 to 21 name; without a
   `MUST-CHANGE` finding, a plain `cargo rullst upgrade` is enough.
5. **Replace the removed deprecated APIs.** Each was deprecated in 12.0.0
   (`schema_diff` in 13.0.0-alpha.5) and has a replacement that reports a
   configuration error at start-up instead of failing later:
   - Mail (`V13-MAIL-DEPRECATED-REMOVED`): `ResendDriver::new` and
     `AwsSesDriver::new` become `try_new`, `Message::with_open_tracking` and
     `with_click_tracking` become `try_with_open_tracking(url, secret,
     campaign)?` and `try_with_click_tracking(url, secret)?`, and the
     `TrackingEngine` helpers `generate_open_token`, `generate_click_token`,
     `inject_open_pixel` and `rewrite_links` become their `try_` forms,
     which return a `TrackingError`.

      instead of `DateTime<Utc>`, `rullst::orm::DateTime` instead of
      `NaiveDateTime`, `rullst::orm::Date` instead of `NaiveDate` and
      `rullst::orm::Time` instead of `NaiveTime` (inside `Option` too), set
      them with `Timestamp::now()` or from jiff values (`.into()`, `.parse()`),
      and pass them as query values. Replace `rullst::orm::chrono` paths with
      `rullst::orm::jiff` or your own `jiff = "1"`. The columns keep their
      bytes, so no data migration runs.
    - Core (`V13-LOCALE-JIFF-DATES`): pass a jiff civil value, or
      `&zoned` for a `jiff::ZonedDateTime` in the visitor's zone, to
      `format_date`, `format_time` and `format_datetime`. Pass an ORM value
      itself or a reference to it (`locale.format_date(&day,
      DateStyle::Short)` with `day: rullst::orm::Date`), or the jiff value
      behind it (`*day`).
    - Mail and Capital (`V13-MAIL-JIFF-TIMESTAMPS`,
      `V13-CAPITAL-INVOICE-JIFF-DATE`): pass a `jiff::Timestamp` to
      `send_at`, `with_scheduled_at`, the `expires_at` of
      `PasswordResetAt` and `EmailLoginAt`, and `Invoice::new`.

    Since the 13.0.0-rc.1 CLI, `V13-LOCALE-JIFF-DATES` and
    `V13-CAPITAL-INVOICE-JIFF-DATE` leave a call alone when the file shows
    that its value is a jiff one: a `jiff::`, `civil::`, `Zoned` or
    `Timestamp` path, an ORM type's path (`rullst::orm::Timestamp::now()`),
    a parameter, binding or struct field of such a type, a function of the
    file that returns one, or a chain through `.in_tz(..)`. A read of a
    field the file does not declare as chrono, such as a field of a model
    declared in another file, is left alone too, also (since the
    13.0.0-rc.2 CLI) through `?`, `.clone()`, `.unwrap()` or an
    `.unwrap_or_else(..)` whose fallback is not chrono
    (`charge.paid_at.unwrap_or_else(Timestamp::now)`). Another value whose
    type the file does not show is still reported, so an application that
    finished the move can still see such calls with `--all-rules` or
    `--from`; they are must-change findings, so check that each compiles
    and continue with `--keep-on-failure`.

    Code that keeps chrono for its own work declares `chrono` itself and
    converts where it meets Rullst; its own SQLx queries that bind or read
    chrono values need the `chrono` feature on its own `sqlx` dependency.
    See [moving off `chrono`](#moving-off-chrono) for the type table, the
    range limits and examples.

    Code moved from chrono to jiff mostly changes method names. The ORM
    types have the common operations themselves, returning ORM types, and
    dereference to the jiff value (`*at`) for the rest of jiff's methods.
    They have no `+` or `-` operators, because jiff's panic on overflow; the
    checked and saturating methods report it instead:

    | chrono | jiff |
    | :--- | :--- |
    | `value.format("%d/%m/%Y")` | `value.strftime("%d/%m/%Y")`: `%Y`, `%m`, `%d`, `%H`, `%M`, `%S`, `%A` and `%B` mean what they meant, but chrono's `%f` (always nine digits) is jiff's `%9f` or `%N`, because jiff's `%f` writes only the digits needed |
    | `NaiveDate::parse_from_str(text, "%Y-%m-%d")` | `jiff::civil::Date::strptime("%Y-%m-%d", text)`: the format comes first |
    | `at.timestamp()` | `at.as_second()` (`as_millisecond()` for `timestamp_millis()`) |
    | `day.month0()`, `day.month()` | `day.month() - 1`, `day.month()`: `year()` is an `i16` and `month()`, `day()`, `hour()` are `i8`, so cast where code expected `i32` or `u32` |
    | `NaiveDate::from_ymd_opt(2026, 11, 19)` | `jiff::civil::Date::new(2026, 11, 19)`, which returns a `Result` (`i16`, `i8`, `i8` arguments) |
    | `day.iter_days()` | `day.series(1.day())` (`use jiff::ToSpan`) |
    | `day + Duration::days(n)` | `day.saturating_add(n.days())` or `day.checked_add(n.days())?` on a `Date` or `DateTime` (`use jiff::ToSpan`); a `Timestamp` has no calendar, so `at.checked_add(SignedDuration::from_hours(24 * n))?`, and its `saturating_add` returns a `Result` that is an error for a `Span` with units above hours. `checked_sub` and `saturating_sub` subtract |
    | `day.succ_opt()`, `day.pred_opt()` | `day.tomorrow()?`, `day.yesterday()?` on a `Date` or `DateTime` |
    | `(later - earlier).num_days()` | `later.days_since(earlier)` or `earlier.days_until(later)` on an ORM `Date` (whole calendar days, an `i64`); `later.duration_since(earlier)` and `duration_until` on an ORM `Timestamp`, `DateTime` or `Date` give a `SignedDuration` (`as_secs() / 86_400` for whole days of 24 hours). jiff's `Span`, which jiff's own `since` and `until` return, has no `num_days`: for two jiff dates, `later.since(earlier)?.get_days()` |
    | `at.date()`, `at.time()` | `rullst::orm::DateTime`'s `date()` and `time()`, which return `rullst::orm::Date` and `Time` |
    | `at.to_rfc3339()` | `rullst::orm::Timestamp::to_rfc3339()`, byte for byte chrono's output (`2026-10-15T09:30:00.500+00:00`), also for a `jiff::Timestamp` through `rullst::orm::Timestamp::from(at).to_rfc3339()`. jiff's own `Display` (`to_string()`) writes `Z` instead of `+00:00` and the shortest fraction, which changes the text of a JSON export or a test expectation |
    | Comparing an ORM value with a jiff value | E0308, "have similar names, but are actually distinct types": compare like with like, `*orm_value <= jiff_value` or `orm_value <= rullst::orm::DateTime::from(jiff_value)` ([moving off `chrono`](#moving-off-chrono)) |
21. **Review messaging schedules for POSIX cron** (Messaging schedules use
    the scheduler's cron syntax row, `V13-MESSAGING-CRON-POSIX`).
    `RecurringDefinition::new` now reads a new definition's expression as
    Core's `Scheduler` does. Review each finding:
    - A schedule an earlier version already stored keeps its old meaning
      (deprecated until 14.0). Leave its expression exactly as it is:
      creating it again under the same name with a changed expression fails
      with `RecurringError::LegacyDefinition`. To migrate it, cancel it and
      create the POSIX expression under a new name; a cancelled name is never
      reused. `RecurringDefinition::posix_equivalent()` of the stored
      definition (deserialized from its JSON) gives that expression when
      one exists.
    - For a schedule first created after the upgrade, write POSIX: move each
      weekday number down by one (`2-6`, Monday to Friday, becomes `1-5`;
      names stay) and, where the expression restricts both the day of the
      month and the weekday, restrict one and check the other when the
      message is handled, because a day that matches either one now runs it.
      The finding's note gives a string literal's POSIX form when the rewrite
      is mechanical.

    `RecurringDefinition::new` refuses a field that starts or ends with `,`,
    `-` or `/` (`1, 2 * * *`, `/5 * * * *`) or runs a number into a name
    (`1jan`), stored or not: stop creating such a schedule in code, or cancel
    it and create a POSIX expression under a new name.
    See [Messaging schedules and POSIX cron](#messaging-schedules-and-posix-cron).
22. **Dependencies and feature graphs** (no rule).
    - `cargo rullst make:cors-jwt` middleware generated earlier keeps the
      `jsonwebtoken` 11 its project declares. To move it to 12, the version
      `rullst-connect` and `rullst-auth` (`jwt`) now use, handle the
      `Result` that `EncodingKey::from_secret` and
      `DecodingKey::from_secret` now return (an empty key is refused)
      (`V13-JSONWEBTOKEN-12` reports the calls while a manifest declares
      `jsonwebtoken` 11 or earlier).
    - An application that turns on `ed25519-dalek`'s precomputed tables
      through feature unification declares
      `ed25519-dalek = { version = "3", default-features = false, features = ["fast"] }`;
      a 2.x requirement builds a second copy and leaves the tables off
      (`V13-ED25519-DALEK-3` reports one in a workspace that builds
      `rullst-iot` or `rullst-connect`).
    - `JsonSchemaPolicy` (`jsonschema` 0.61.2) answers `422` to some bodies
      that 0.60 accepted: `.` in `pattern` and `patternProperties` no longer
      matches `\r`, U+2028 or U+2029, and `date-time`, `date` and `time`
      values with a `+`, `,`, `-`, `.` or `/` where a digit belongs are
      refused. No rule locates them: the bodies are runtime input.
    - With `studio` but without `capital`, `/studio/capital` shows a notice
      instead of the revenue dashboard, `/api/revenue` answers 404 and
      `rullst::studio::revenue_dashboard` is gone: enable `capital` to keep
      them. An application whose own code makes rustls connections and
      relied on `orm` installing aws-lc-rs as the process default enables
      the facade's `tls` feature (TLS stack of SQLite-only builds row).
23. **Update scripts, CI and other tools.** Where a workflow or script
    installs a pinned CLI (`cargo install cargo-rullst --version
    =13.0.0-alpha.5`), pin `=13.0.0-alpha.6`. Check the health-probe scripts
    of step 8 and any client that posts to the development server (step 10).
24. **Validate.** Run `cargo rullst upgrade` again. It makes no further version
    edits and checks the result with `cargo fix` and `cargo check --locked`.
25. **Verify** with the production feature set: `cargo build`, `cargo test`
    and `cargo clippy --all-targets -- -D warnings`; then, on staging, sign-in
    and sign-out, every form and htmx request (CSRF), every page with the
    browser's developer console open to catch CSP violations, the health
    probes, the scheduled tasks and the access log, before production.

Optional, once the upgrade runs in production: **SQLite applications can
turn on WAL** (SQLite WAL journal row; `V13-SQLITE-WAL-AVAILABLE` reports a
SQLite project without `sqlite_journal_mode`, for information: nothing
changes until you opt in, and `sqlite_journal_mode = "delete"` or a
`rullst-upgrade: reviewed V13-SQLITE-WAL-AVAILABLE` marker keeps the rollback
journal without a finding). Add
`sqlite_journal_mode = "wal"` under `[database]` in `Rullst.toml`, after
switching your backups to `sqlite3 ".backup"` and only when the database is
on a local disk of the one host that runs the application.

## Upgrading an alpha.6 application to rc.1

This checklist moves an application from 13.0.0-alpha.6 to 13.0.0-rc.1.
To go straight to 13.0.0-rc.2, use `13.0.0-rc.2` wherever it says
`13.0.0-rc.1`, then follow
[Upgrading an rc.1 application to rc.2](#upgrading-an-rc1-application-to-rc2).
After the alpha.6 freeze, rc.1 adds fixes, documentation and changes the
maintainer approved one by one; two of them rename or remove public API, and
several change what a working alpha.6 deployment does at start-up or on a
request. Code that `cargo rullst` generated earlier is never rewritten.

1. **Prepare.** Work on a branch with a clean tree and a committed
   `Cargo.lock`, record the current `cargo test` result, and back up every
   database.
2. **Install the rc.1 CLI** (`cargo install cargo-rullst --version
   =13.0.0-rc.1 --locked --force`; `rullst --version` must print
   `13.0.0-rc.1`) and run `cargo rullst upgrade --dry-run` before changing
   the versions. It applies the rules introduced after 13.0.0-alpha.6:
   `V13-IOT-SIMULATORS-REMOVED`, `V13-LABS-VARIANTS-RENAMED` and
   `V13-AUTH-SESSION-EPOCH-CALLS`. If the manifests already pin
   `=13.0.0-rc.1`, add `--from 13.0.0-alpha.6`.
3. **The two API changes.** `rullst-iot` no longer has the
   `experimental-simulators` feature or its `Simulated*` types; remove the
   feature and give tests their own fixed bytes (`V13-IOT-SIMULATORS-REMOVED`).
   `rullst-labs` renamed `ExecutionProfile::LinuxExperimental` to
   `ExecutionProfile::PinnedRunner` and `ResultEvidence::Experimental` to
   `ResultEvidence::SignedReceipt`; their serialized names are unchanged
   (`V13-LABS-VARIANTS-RENAMED`).
4. **Empty settings in staging and production** (Empty settings in staging
   and production row; no rule locates them). The `Mail` facade returns
   `MailError::ConfigError` when the selected driver's credential
   (`RESEND_API_KEY`, `SENDPULSE_API_KEY`, the SES proxy token) is empty or
   unset, or `MAIL_HOST` is empty; `AiClient::auto()` returns
   `AiError::ConfigError` when no AI provider is configured, and a client
   from `AutoAiConfig::into_client()` then fails every request. On alpha.6
   both answered with an offline mock. Both resolve staging and production
   as `Server` does: the process `RULLST_ENV`, then `APP_ENV`, then either
   one from `.env`, then `[app] env` in `Rullst.toml`. Set the real value
   before deploying, or an explicit `mock_*` value where the mock is wanted,
   such as a staging server without a provider account.
5. **A mock behind a live AI provider.** In staging and production
   `AiClient::auto()` and `AutoAiConfig::from_env()` refuse a chain in which
   a `mock_*` key sits beside a live one, because the mock would answer
   whenever the live provider failed. Remove the leftover `mock_*` value.
6. **Remote Studio.** The standalone `rullst-studio` answers `403` until you
   open the `http://127.0.0.1:<port>/studio?key=…` address it prints at each
   start; a bookmark of `http://127.0.0.1:5556/studio` stops working.
7. **Local Studio and loopback Nexus.** `LocalStudioAccess` and
   `NexusAuthPolicy::LoopbackOnly` refuse requests that carry a forwarding
   header or use HTTP/1.0, and requests whose `Server` resolved staging or
   production. Building them fails with `LocalAccessRequiresDebugBuild` in
   a debug build whose process `RULLST_ENV` or `APP_ENV` is staging,
   production or invalid; there,
   `NexusAuthPolicy::local_development_or_application` and
   `local_development_or_basic_from_env` select the application's sign-in or
   Basic Auth. A staging debug build that served Nexus without credentials
   needs those credentials now.
8. **SurrealDB graph reads.** `GraphQuery::read_only` accepts only its
   read grammar (`MATCH`, an optional `WHERE`, `RETURN` and `ORDER BY`);
   rewrite a query that uses anything else, such as `OPTIONAL MATCH` or
   `DISTINCT`, or it returns `PolyglotError::InvalidIdentifier`.
9. **OpenAI-compatible endpoints.** `OpenAiCompatibleProvider` and its
   DeepSeek and Ollama presets now give up on a connection that takes more
   than five seconds, as the native adapters do, instead of waiting for the
   whole-request deadline.
10. **Logs.** Requests that `Server`'s own layers refuse (CSRF, the WAF in
    staging and production, the rate limiter, Traffic Shield, machine
    endpoint authentication, lifecycle admission) now get an access-log line
    such as `[HTTP] POST /login -> 403 (0.31 ms) refused by csrf`; a script
    that counts lines sees more of them. A release build serving a
    non-loopback address as development or test logs a `warn` event, and a
    `rullst-connect` callback that still uses the legacy `oauth_state`
    session key logs a deprecation warning.
11. **Database pools.** PostgreSQL and MySQL pools created by `Orm::init*`
    ping a connection before handing it out only after 500 ms idle, so a
    connection that dies sooner fails its next query once.
12. **Optional.** Code generated by the rc.1 CLI also refuses empty settings
    in staging and production: the Turso starter (`TURSO_DATABASE_URL`),
    billing (`BILLING_API_KEY`, `BILLING_WEBHOOK_SECRET`, now in staging too)
    and `make:oauth`, whose `environment()` reads `.env` and `[app] env`
    before `Server` starts. Compare with a project the rc.1 CLI generates and
    copy what you want. The session registry's table can cascade deletions
    from `users`, as the
    [alpha.5 to alpha.6 checklist](#upgrading-an-alpha5-application-to-alpha6)
    describes.
13. **Verify.** Switch every Rullst requirement to `=13.0.0-rc.1`, run
    `cargo update -p rullst --precise 13.0.0-rc.1`, `cargo test` and a start
    with `RULLST_ENV=staging` and the deployment's settings, before the
    production deployment. Then search the whole repository for the previous
    version string (`grep -rn 13.0.0-alpha.6 .`, skipping `target/`) and
    update what the manifests do not cover: the CI files that install
    `cargo-rullst` (`RULLST_CLI_VERSION`, which otherwise keeps installing
    the alpha.6 CLI against an rc.1 project and still passes), README
    badges and text, deployment documentation, and any kit or generated
    project that embeds a Rullst `Cargo.toml` and `Cargo.lock` (its
    generated manifests, course texts and test assertions too). In an
    embedded project, `cargo update -p rullst --precise 13.0.0-rc.1` moves
    only the Rullst packages and leaves the other locked versions alone.
    `cargo rullst upgrade` does not list these occurrences.

## Upgrading an rc.1 application to rc.2

13.0.0-rc.2 fixes two defects found in rc.1. It removes and renames nothing;
it adds `rullst::config::project_environment()` and `PartialEq` for the
configuration structs. `cargo rullst upgrade` has no rule for rc.2.

1. **Change the pins.** Switch every Rullst requirement from `=13.0.0-rc.1`
   to `=13.0.0-rc.2`, install the rc.2 CLI (`cargo install cargo-rullst
   --version =13.0.0-rc.2 --locked --force`), and update the other places
   step 13 of the [rc.1 checklist](#upgrading-an-alpha6-application-to-rc1)
   lists (`RULLST_CLI_VERSION` in CI, README badges, deployment
   documentation, embedded kits). The next `cargo build` moves the locked
   Rullst packages; between rc.1 and rc.2 no other dependency changed.
2. **A configuration read before `Server` starts** (Early configuration read
   row). If code calls `RullstConfig::global()` before `Server` starts, the
   reads after start-up now see `Rullst.toml`, and `Server` logs a warning
   that names the early read when the two differed. A reference taken before
   start-up keeps the defaults: read the configuration after `Server`
   starts, or call `rullst::config::project_environment()` where only the
   environment is needed.
3. **Studio and Nexus at build time** (Loopback environment at build time
   row). In a debug build whose `.env` or `[app] env` sets staging,
   production or an invalid value, or whose `.env` or `Rullst.toml` is
   malformed when it has to be read, the local Studio and an explicit
   loopback Nexus policy now fail to build with
   `LocalAccessRequiresDebugBuild`, as they already did for the process
   variables. `NexusAuthPolicy::local_development_or_basic_from_env()`
   (generated by `cargo rullst add nexus`) then requires the
   `NEXUS_ADMIN_USERNAME` and `NEXUS_ADMIN_PASSWORD` credentials, so start-up
   stops without them, and Basic Auth refuses requests that lack verified
   TLS; `local_development_or_application()` (the SaaS starter) uses the
   application's sign-in. Run local development with a development or test
   environment, or give a shared environment an authenticated policy.
4. **Verify.** Run `cargo test` and compare with the rc.1 result, start the
   application with its staging settings and check the start-up log for the
   new warning.

## Why the candidate uses a new major

Adding optional privacy APIs, a new crate or more features does not by itself
require a major version. A fully compatible increment would belong in a minor
release under the [compatibility policy](compatibility-policy.md).

The current candidate does change a supported CLI/configuration contract:
13.0 removes commands and public items that 12.x applications can use (the
rows marked Breaking above list them), for example
`cargo rullst make:omni` and `cargo rullst omni`, the `offline-sync` feature
with `rullst::offline_sync`, and the `Commands::MakeOmni`/`Commands::Omni`
variants and `OmniPlatformChoice` of the `cargo-rullst` library. This
intentional change supports retaining v13 for the synchronized release train;
it does not mean every application's Rust code needs rewriting. The Omni row
above documents the replacement.

A green version-aware SemVer job alone cannot establish that this candidate
could be renamed to 12.2. The current command derives the release type from the
manifest; the 12.1-to-13 comparison permits major changes. The hosted comparison
at `4773171a` reported **0 executed checks and 254 skipped checks** for compared
libraries. Treat that as no Rust API compatibility result, not as proof that
breaking changes are absent. Any reconsideration as a minor release requires
an explicit minor-level API comparison plus review and regression tests for
CLI, configuration, serialized contracts and generated consumers. Resolve the
known Android compatibility change before making that claim.

## Use the target-major CLI

A v12 CLI cannot learn v13 migration rules just by downloading another binary:
install the v13 CLI, then start a **new invocation of that v13 CLI** for the
project migration.

To evaluate the published prerelease, install its CLI from crates.io. Cargo
never selects a prerelease on its own (`cargo install cargo-rullst` installs
the end-of-life 12.x CLI), so name the exact version:

```bash
cargo install cargo-rullst --version =13.0.0-rc.2 --locked
rullst --version
```

The output must identify `13.0.0-rc.2`. The projects it generates pin the
framework packages with `=13.0.0-rc.2`, as described at the top of this
guide. Reinstall with `--force` to go back to 12.x (`--version '^12'`) or to
move to a later prerelease.

To evaluate unreleased `main` changes instead, build the CLI from the reviewed
checkout:

```bash
cargo build --locked -p cargo-rullst
./target/debug/rullst --version
```

Use that explicit executable path instead of assuming a `rullst` already on
`PATH` is the same binary. This is a local source build, not authenticated
published distribution evidence. Generated projects then refer to the matching
local framework packages; keep that checkout available and review those paths.
The final package rehearsal must independently prove registry-based consumers.

## Prepare, verify, review and apply

Keep a restorable application and database backup. Quiesce writers during file
application/recovery and review the application's ignored files, toolchain and
Cargo configuration. The Git working directory's tracked and non-ignored files
are copied into private preparation storage; the root `Cargo.lock` is included
even if ignored. Typical ignored secret files and build outputs are excluded.

Using the selected v13 executable, the structured sequence is:

```text
rullst update project prepare --project /path/to/app --to 13.0.0-alpha.6 --json
rullst update project verify --prepared PREPARED_DIRECTORY --dry-run --json
rullst update project verify --prepared PREPARED_DIRECTORY --allow-project-code --json
rullst update project review --verified VERIFIED_DIRECTORY --json
rullst update project apply --verified VERIFIED_DIRECTORY --approved-review REVIEW_SHA256 --json
```

Use the directories returned by the preceding commands. Inspect the complete
review before supplying its digest. Verification executes trusted build scripts,
procedural macros and tests, and is offline by default; the private copy is not
a sandbox. Supply `--allow-network` only after reviewing that separate need.
Select the application's actual feature policy (`--features`, `--all-features`
or `--no-default-features`) instead of assuming default features cover production.

Preparation accepts supported versioned dependency declarations and preserves
their TOML structure. Unversioned path/git dependencies, ambiguous ranges,
unsupported source majors, stale inputs and unresolved source findings require
manual review. Verification requires every managed framework package in the
candidate lockfile to resolve to the selected exact target. It runs locked
workspace checks and tests before review can authorize manifest/lockfile edits.

After application, source-file recovery uses the same reviewed operation:

```text
rullst update project recover --verified VERIFIED_DIRECTORY --approved-review REVIEW_SHA256 --json
```

Recovery rejects later conflicting edits. It restores the recorded manifest and
lockfile states; it cannot undo database writes, network calls, provider effects
or other external effects of application tests. It does not deploy either state.

## Privacy remains an application decision

The preview [privacy guide](privacy-age-assurance-roadmap.md) documents the explicit local source
selection and authenticated SaaS installation contracts. Do not enable an
age restriction merely because the framework offers one. Select a server-owned
policy for the actual action and accept declarations only where that policy
permits their assurance level. Production rejects unsupported stronger methods
and process-local replay storage.

Consent-store files, replay databases, encryption/signing keys, subject/tenant
binding and retention/restore procedures need their own deployment plan.
Shared-local SQLite consent is not a multi-host consensus store; the optional
`consent-postgres` store shares consent through one authoritative PostgreSQL
database. The profile
export remains available independently of optional-consent configuration, but it
only exports the authenticated account fields supported by its adapter.

## Evidence and remaining acceptance

`update_project_cli` exercises distinct 12.1.0 and 13 packages through real Cargo
resolution, prepare/verify/review/apply/recover, changed inputs and wrong approval
digests. Those intentionally tiny packages prove the updater protocol, not the
framework's runtime API compatibility. The separate generated-starter suites
compile actual framework source and execute application/authentication tests;
the age/privacy suites also exercise both opt-in installation orders.

Final release admission still requires the combined exact-commit workspace and
feature/consumer matrix, strict Clippy and formatting, package/native artifact
rehearsals, the required security/fuzz workflows, and this inventory updated for
all admitted changes. Application sandbox/provider journeys and deployment smoke
tests remain distinct from framework CI. See the [SST](spec.md#-12-assisted-framework-upgrade-contract)
and [delivery plan](v13-delivery-plan.md).
