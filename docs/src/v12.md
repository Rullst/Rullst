record of that release; it is no longer a development backlog or launch
checklist.

## What v12 stabilizes

Version 12 stabilizes the **bounded public contracts** described by the
[Single Source of Truth](spec.md). Major delivered areas include the Axum/Tokio
runtime and CLI scaffolding, relational ORM foundations, typed Turso support,
bounded optional persistence adapters, authentication and security controls,
provider-oriented AI, payments and mail, broker-neutral local messaging,
Studio and Nexus, and bounded Omni packaging foundations.

“Stable” means the documented v12 APIs and stated boundaries are suitable for
normal SemVer maintenance. It does not mean that every roadmap idea is complete
or that every third-party service, deployment, mobile device, fiscal authority,
or hardware platform has been homologated.

Use these active sources instead of old development percentages:

- [Specification](spec.md) — normative architecture and capability boundaries;
- [Capability status](capability-status.md) — compact implemented/partial/
  roadmap view;
- [Capability ledger](capability-ledger.md) — detailed evidence and limitations;
- [Release audit](v12-release-audit.md) — repository-owned verification record;
- [Changelog](https://github.com/Rullst/Rullst/blob/main/CHANGELOG.md) — exact
  user-facing changes;
- [Workflow guide](https://github.com/Rullst/Rullst/blob/main/WORKFLOWS.md) —
  current automated, scheduled, and manual checks.

## Verification summary

The stable candidate passed the required exact-SHA hosted gates and the tag-only
publication pipeline. The maintained assurance system covers multi-platform
tests, strict linting and formatting, package consumers, documentation,
coverage floors, dependency and source policy, code scanning, generated
applications, DAST, property tests, sanitizers, Miri, Kani, fuzzing, Omni
compile matrices, and release artifact reproduction.

Every result is scoped to its workflow, target inventory, toolchain, commit,
fixtures, and environment. For example, compilation of an unsigned mobile shell
does not prove physical-device behavior or app-store acceptance, and protocol
fixtures do not prove acceptance by a live provider. The
[release audit](v12-release-audit.md) records those evidence boundaries.

## Upgrading to v12

Existing applications should follow the [v12 migration hub](migration-v12.md)
and the guide for their starting line:

- [v5 to v12](migration-v5-to-v12.md);
- [v6 to v12](migration-v6-to-v12.md);
- [v11-era dependencies to v12](migration-v11-to-v12.md).

`cargo rullst upgrade --dry-run` and `cargo rullst upgrade` provide an
assisted, inspectable migration workflow. They do not silently rewrite arbitrary
application semantics; review the generated plan, back up application data,
commit a clean baseline, run migrations in a safe environment, and execute the
application's own tests.

## Maintenance after release

The `12.x` line accepts compatible correctness, security, documentation, and
dependency-maintenance releases. Breaking APIs and substantial new capabilities
belong to v13. Security reports should follow
[`SECURITY.md`](https://github.com/Rullst/Rullst/blob/main/SECURITY.md).

### 12.1.0 delivery checkpoint (unreleased)

The next planned release is **12.1.0**, not another publication of the immutable
12.0.0 archives. Working-source changes are not available from crates.io until
a new version is published. The maintenance candidate now brings together:

- Studio asset/cache routing and Nexus/Portfolio mobile fixes, with migration
  notes for application-owned workaround routes and generated views;
- reviewed dependency and pinned Action updates, with synchronized fuzz locks;
- [SaaS maintenance](saas-v12-1-v13-triage.md), including provider configuration,
  Stripe signature rotation, machine-client WAF defaults and honest operation
  boundaries across the v12 gateway inventory;
- bounded update notices, explicit advisory `cargo rullst update check`, the
  complete managed-package inventory and staged backup restoration;
- the [API reference index](api-reference.md), clearer
  [HTMX/CSRF guidance](tutorials/07-forms-and-validation.md#step-3-send-the-csrf-token-with-browser-forms)
  and existing verification-efficiency improvements.

The explicit checker has bounded private Unix caching and offline reuse. The
Windows owner/DACL implementation cross-compiles with strict Clippy. Its three
native cache contracts and the complete Windows CLI standard shard passed at
`990ddf1cf790cd422c1770a87b3fa19d13ab9ecb` in
[run 35259362060](https://github.com/Rullst/Rullst/actions/runs/35259362060/job/105331464048).
That evidence covers private cache roundtrips/expiry/replacement and rejection
of unsafe ACLs, locks, links and paths; the final candidate still requires all
release gates on its exact source commit.
Its source/age report grants no installation authority. Tauri materializes the
Android Gradle configuration before the standalone Gradle check, and its tutorial
is registered in the documentation inventory gate.

The 2026-09-16 Linux check passed 318 CLI unit/process tests (including
upgrade recovery and Omni tool boundaries), both documentation-inventory tests,
CLI all-target/all-feature strict Clippy, formatting, Action pin validation and
the mdBook build. These targeted local results are not a full workspace,
Windows/macOS or native Android sign-off; the candidate's hosted checks remain
required. Native Android evidence must include the actual signed APK and its
certificate, not just process fixtures or a successful Rust compile.

The [native Android check](https://github.com/Rullst/Rullst/actions/runs/35262089400)
passed at `95225f5e`: a disposable key signed the generated release APK, and
`apksigner` verification plus a DER certificate digest comparison passed.
The certificate parser accepts both signer-label formats emitted by the
supported toolchain and rejects substituted certificates or extra signers.
This covers the generated CI shell, not physical devices or store acceptance.

The [full Rust CI matrix](https://github.com/Rullst/Rullst/actions/runs/35262104284)
passed at `95225f5e`, including all test shards on Linux, Windows and macOS,
strict workspace Clippy/format, database/provider matrices and public feature
boundaries. Subsequent checkout, billing, ORM and upgrade changes require a
new exact-commit run; this checkpoint does not certify those later changes or
replace the other publication gates.

The [follow-up matrix](https://github.com/Rullst/Rullst/actions/runs/35267853511)
at `e1d8fe4d` finished with 35 successful and seven failed jobs. The failures
came from unconditional enum codecs in isolated ORM builds and an unexpanded
billing persistence placeholder in the CLI template fixture. `98977d0b` and
`c5ae541d` correct those causes with local regression evidence. Later customer
and inbox additions still need a full candidate run; this failed checkpoint is
not release admission.

The sixteen public manifests and their internal minimum requirements now use
the **unpublished 12.1.0 candidate**. The workspace and ten fuzz lockfiles are
synchronized without changing external dependency versions. The metadata
preflight validates all sixteen packages and their topological order. This
version preparation creates neither a release tag nor a registry publication.

Additional local gateway review passes 157 Capital tests with Actix and strict
all-target Clippy. Lemon Squeezy now validates subscription lifecycle/state,
store/mode/identities and expiry; InfinitePay's unreviewed live callback fails
explicitly. New generated billing is contained to local development fixtures:
real/mixed credentials return 503 before SQL/provider calls or replay claims.
SQLite/Turso materialized contracts cover checkout, portal, direct handler and
the actual webhook middleware, preserving rollback/retry and ownership tests.
All ten scaffold contracts and CLI all-feature/all-target Clippy pass. Existing
SaaS controllers require an application-owned migration.

**Release blockers still open:** validate the contained billing boundary in the
full candidate matrix (complete durable identity/event integration before
enabling the generated live operation),
review backend isolation, finish verified CLI installation and isolated project
preparation/review/application flow;
validate recovery and consent across supported platforms; complete the exact
candidate's dependency, compatibility, package-consumer and release evidence.
The existing `upgrade` transaction is useful, but these new stages must not be
described as implemented merely because `update check` works. The
[acceptance plan](https://github.com/Rullst/Rullst/blob/v13/ROADMAP.md#safe-update-experience)
defines those boundaries. Future v13 migration rules remain v13 work.

Do not regenerate an existing application over local changes. Updating the CLI
or framework dependencies neither rewrites application-owned blueprint files
nor redeploys the Azure demonstrations. New capability development should focus
on v13 after this compatible minor is validated and released; v12 then receives
necessary maintenance by exception.

The maintenance candidate also adds default Rullst-branded Omni icons applied
after native initialization, application-owned Android release signing and
upgrade recovery fixes for macOS root aliases and Windows strict linting.
See [Android signing](tutorials/49-omni-android-signing.md). These changes are
unreleased; native CI and cross-platform recovery acceptance remain required.
