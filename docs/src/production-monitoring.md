# Production monitoring endpoint

Rullst Studio's local pages are a development tool: they run only in debug
builds, on `127.0.0.1:5555`, and read the local process. To watch an application in
staging or production, Rullst 13 (since 13.0.0-alpha.3) adds a read-only
monitoring endpoint to the application itself:

```text
GET /_rullst/monitor/v1
GET /_rullst/monitor/v2   # since 13.0.0-alpha.6
```

It answers a JSON document, versioned as `rullst.monitor.v1`, with request
rates and latency per route pattern, status classes, queue depth and worker
activity, possible N+1 queries and the process radar. Since 13.0.0-alpha.6,
`/_rullst/monitor/v2` answers `rullst.monitor.v2`: the same fields plus
[sampled request traces and the security radar](#version-2-traces-and-the-security-radar).
Both paths are mounted together and share the credentials and limits below.
Neither contains database rows, request data or configuration. It is phase 1 of the Studio
production monitor delivered in
[13.0.0-alpha.3](https://github.com/Rullst/Rullst/blob/main/CHANGELOG.md#1300-alpha3---2026-10-23);
phase 2 is the [standalone Studio](#watch-your-projects-from-studio) on your
machine, which reads this endpoint for several projects. Any HTTPS client
(curl, a script, an uptime tool) can read it too.

The endpoint is **off by default**. The threat model is
[`TM-STUDIO-2`](threat-models.md#tm-studio-2--production-monitoring-endpoint).

## Enable it

Two things are needed: the application mounts the monitor, and the operator
gives it a credential.

```rust,no_run
use rullst::Server;
use rullst::monitor::Monitor;
use rullst::routes;
use rullst::routing::get;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    Server::new(routes![get("/" => || async { "OK" })])
        .with_monitor(Monitor::new().with_application(
            env!("CARGO_PKG_NAME"),
            env!("CARGO_PKG_VERSION"),
        ))
        .run(3000)
        .await?;
    Ok(())
}
```

Then generate a token of at least 32 random bytes and set it where the server
reads its configuration, the process environment or `.env`:

```bash
openssl rand -base64 32   # or: openssl rand -hex 32
```

```env
RULLST_MONITOR_TOKENS=<the generated value>
```

When the server starts it validates every
token: fewer than 43 base64/base64url or 64 hexadecimal characters, other
characters, fewer than ten distinct characters or a placeholder such as
`changeme` stop start-up with a configuration error that names the token's
position, never its value. Without any token and without an application
authorizer, `with_monitor` mounts nothing: `/_rullst/monitor/v1` answers `404`
and requests are handled exactly as without the monitor. So the code can stay
in place and the operator decides per deployment.

`Monitor::with_token` adds a token from your own secret store, in addition to
the environment's.

Projects generated by `cargo rullst new` with the Blank, API or SaaS starter
(and the LMS example) already carry these lines in `src/main.rs`, commented out
in the server chain, and list `# RULLST_MONITOR_TOKENS=` in `.env` and
`.env.example`, also commented out. To enable the monitor, uncomment the
`.with_monitor(...)` call, generate a token and set `RULLST_MONITOR_TOKENS` in
the deployment's environment (keep real tokens out of `.env.example`). Until
then nothing is mounted. Projects generated earlier add the call as shown
above.

Read it with the token in the `Authorization` header, never in the URL:

```bash
curl -fsS -H "Authorization: Bearer $RULLST_MONITOR_TOKEN" \
  https://shop.example/_rullst/monitor/v1
```

### Use the application's own sign-in

An administrator who is signed in to the application can read the endpoint
with their session instead of a token, the way Nexus accepts
`NexusAuthPolicy::application`. Implement `MonitorAuthorizer`:

```rust,no_run
use rullst::http::request::Parts;
use rullst::monitor::{Monitor, MonitorAccess, MonitorAuthorizer, MonitorAuthorizerError};

/// Admits requests an outer session layer marked as coming from operators.
struct Operators;

impl MonitorAuthorizer for Operators {
    async fn authorize(&self, request: &Parts) -> Result<MonitorAccess, MonitorAuthorizerError> {
        Ok(match request.headers.get("x-verified-operator") {
            Some(_) => MonitorAccess::Allow,
            None => MonitorAccess::SignIn,
        })
    }
}

let monitor = Monitor::new().with_authorizer(Operators);
```

The authorizer is asked for every request without a valid token. `Allow`
serves the document, `SignIn` answers `401`, `Deny` (a signed-in user without
the permission) answers `403`, and an error answers `503` and logs the
reason. Browsers cannot read the endpoint from another page; see below.

### Report queues

```rust,no_run
# use rullst::monitor::Monitor;
# use std::sync::Arc;
# fn monitor(queue: Arc<rullst::Queue>) -> Monitor {
// The same Arc<Queue> the application's workers use.
let monitor = Monitor::new().with_queue("default", queue.clone());
# monitor
# }
```

Up to 16 queues, named with 1 to 64 letters, digits, `.`, `_` or `-`.

## Put it behind your proxy or VPN

In staging and production the endpoint refuses plain HTTP with `426 Upgrade
Required`, before it looks at credentials. A request is accepted when:

- a reverse proxy listed in `Server::trusted_proxies` (or `[security]
  trusted_proxies`) with `trust_forwarded_proto` reported `https`;
- the application terminates TLS itself and inserts
  `MonitorVerifiedTls::from_trusted_tls_termination()` into the request's
  extensions from its TLS listener; or
- `Monitor::allow_loopback_plaintext(true)` is set and the request comes
  directly from a loopback address, names a loopback `Host` and carries no
  forwarding header: an SSH tunnel (`ssh -L 9000:127.0.0.1:3000 server`) or a
  sidecar on the same host.

A forwarded header from any other peer, or an absolute `https://` request
target, is not evidence. If a token ever crossed a network in plain text,
rotate it.

Exposure is your choice. The safest setups keep the path off the public
internet: allow it only from your VPN (WireGuard, Tailscale) or office ranges
in the reverse proxy, for example with nginx:

```nginx
location /_rullst/monitor/ {
    allow 100.64.0.0/10;   # Tailscale
    deny all;
    proxy_pass http://127.0.0.1:3000;
}
```

## Rotate tokens

`RULLST_MONITOR_TOKENS` holds up to eight comma-separated tokens, and any of
them is accepted. To rotate without downtime:

1. add the new token: `RULLST_MONITOR_TOKENS=<new>,<old>`, and restart or
   redeploy (tokens are read at start-up);
2. switch your monitoring clients to the new token;
3. remove the old one and restart again.

Give each client (each developer machine, each script) its own token, so you
can revoke one by removing it.

## Responses

| Status | When |
| --- | --- |
| `200` | Document served (`Content-Type: application/json`). |
| `401` | No credential, or an invalid one: always the same empty answer, with `WWW-Authenticate: Bearer realm="rullst-monitor"`. |
| `403` | The request carries an `Origin` header or a `Sec-Fetch-Site` of `cross-site`/`same-site` (a browser page), or the authorizer denied it. |
| `404` | The monitor is not mounted. |
| `405` | Any method other than `GET`/`HEAD`. |
| `426` | Staging or production without TLS evidence. |
| `429` | More than 30 requests in a burst (one more each second) from one client, with `Retry-After: 1`; or, after 10 invalid presented tokens, every request from that client until one more attempt is allowed every 90 seconds (`Retry-After: 90`), without evaluating credentials. |
| `503` | The application authorizer failed. |

Every answer of the mounted endpoint carries `Cache-Control: no-store` and
`X-Content-Type-Options: nosniff`; staging and production also add the usual
security headers. The endpoint adds no CORS headers, and because it refuses
any request with an `Origin`, an application CORS allowlist never releases it
to a browser page. Clients are identified per IPv4 address or IPv6 /64, as
resolved through trusted proxies: configure them, or every client behind your
proxy shares one budget and one lockout. These limits are per process. The
server's own rate limiter and Traffic Shield apply to the endpoint like any
route, and the endpoint's own requests are not counted in its statistics.

## What it reports

```json
{
  "schema": "rullst.monitor.v1",
  "generated_at": 1792648800,
  "application": { "name": "shop", "version": "1.4.0" },
  "framework": { "name": "rullst", "version": "13.0.0-rc.1" },
  "uptime_seconds": 86400,
  "process": {
    "memory_rss_mb": 48.2,
    "cpu_usage_percent": 3.5,
    "active_tokio_tasks": 42,
    "tokio_latency_micros": 18
  },
  "http": {
    "window_seconds": 300,
    "route_limit": 256,
    "routes_overflowed": false,
    "requests_total": 120345,
    "status_total": { "1xx": 0, "2xx": 118000, "3xx": 1200, "4xx": 1100, "5xx": 45 },
    "bytes_total": 1052672000,
    "window": {
      "covered_seconds": 271,
      "requests": 1626,
      "requests_per_second": 6.0,
      "status": { "1xx": 0, "2xx": 1600, "3xx": 10, "4xx": 15, "5xx": 1 },
      "latency_ms": { "p50": 2.5, "p90": 10.0, "p95": 25.0, "p99": 100.0, "max": 412.3 },
      "bytes": 14212000
    },
    "routes": [
      {
        "method": "GET",
        "route": "/orders/{id}",
        "requests_total": 5400,
        "status_total": { "1xx": 0, "2xx": 5300, "3xx": 0, "4xx": 98, "5xx": 2 },
        "bytes_total": 44236800,
        "window": { "covered_seconds": 271, "requests": 80, "requests_per_second": 0.295,
                    "status": { "1xx": 0, "2xx": 79, "3xx": 0, "4xx": 1, "5xx": 0 },
                    "latency_ms": { "p50": 5.0, "p90": 10.0, "p95": 10.0, "p99": 25.0, "max": 19.8 },
                    "bytes": 655360 }
      }
    ]
  },
  "database": {
    "state": "observed",
    "queries_total": 9876,
    "n_plus_one": {
      "threshold": 3,
      "findings_total": 12,
      "findings": [
        { "method": "GET", "route": "/orders/{id}", "fingerprint": "LineItem.find (line_items)",
          "requests": 12, "max_occurrences": 25, "last_seen": 1792648790 }
      ]
    }
  },
  "queues": [
    { "name": "default", "pending": { "state": "observed", "count": 3 },
      "in_flight": 1, "completed_total": 5000, "failed_total": 4,
      "retried_total": 2, "stalled_recovered_total": 0 }
  ]
}
```

- **Versions:** `application` is what `Monitor::with_application` names, and
  `framework` the Rullst release. Since 13.0.0-alpha.6 the public `/health`
  and `/ready` probes no longer report the framework release, and report the
  application's only through `health_router_with_version`, so this
  authenticated document is where the framework version appears.
- **Routes** are keyed by the matched route pattern (`/orders/{id}`) and a
  normalized method (the standard methods, else `OTHER`); requests that matched
  no route are counted as `(unmatched)`. At most 256 method and pattern pairs
  are kept; later ones share `{"method": "*", "route": "(other)"}` and
  `routes_overflowed` becomes `true`.
- **Totals** count since the process started. The **window** covers the last
  five minutes in one-minute slots; `covered_seconds` says how much of it has
  elapsed (less right after start-up), and `requests_per_second` is
  `requests / covered_seconds`, rounded to thousandths.
- **Latency percentiles** come from a fixed histogram (bucket bounds from
  0.1 ms to 10 s): each value is the upper bound of its bucket, capped at the
  window's maximum, and `latency_ms` is `null` without requests in the window.
  Durations run from the outermost framework layer to the response headers.
- **Bytes** (since 13.0.0-alpha.5) are the response bodies as sent, after any
  compression the application applies and without headers or TLS, in the
  same totals and window as the requests: a body of known length counts when
  the response is recorded, a streamed body (server-sent events, a download)
  when it ends or the client goes away, and a `HEAD` response counts none.
  `cargo rullst footprint --monitor-url` reads them per route next to its lab
  figures ([resource figures](footprint.md#production-bytes-from-the-monitor)).
- **Database** counts the outermost ORM operations started by requests and
  lists repeated operations as the ORM's static `Model.operation (table)`
  fingerprint, never SQL text or values (at most 64 entries, the least
  recently seen replaced first). It needs the framework's tracing subscriber
  (`Server` installs it) and a `RUST_LOG` that keeps `rullst_orm` at `info`;
  otherwise it reports `{"state": "unavailable", "reason":
  "subscriber_not_installed"}` or `"orm_spans_filtered"`. That subscriber
  creates the ORM spans only once the monitor (or the development dashboard)
  is mounted (since 13.1.0), so a process without either does not pay for
  them.
- **Queues**: `pending` is read from the queue store (all workers, with a
  250 ms limit per queue; `timeout` or `driver_error` otherwise, never the
  driver's message). The other counters cover this process's workers since
  start: running handlers, completed, failed (error, panic, timeout, no
  handler), retried (requeued at shutdown, handed back for lack of a handler,
  or `Queue::retry_failed_job`) and stalled leases recovered.

What it never contains: raw paths, query strings, headers, cookies, client
addresses, user identifiers, request or response bodies, SQL text or bound
values, error messages, environment variables or configuration values. Route
patterns and queue names are chosen by your code, so keep personal data out of
them.

### Version 2: traces and the security radar

`GET /_rullst/monitor/v2` (since 13.0.0-alpha.6) answers every field above
with `"schema": "rullst.monitor.v2"`, plus two sections:

```json
{
  "traces": {
    "sample_limit": 50,
    "sampled_total": 1834,
    "requests": [
      { "at": 1792648790, "method": "GET", "route": "/orders/{id}", "status": 503,
        "duration_ms": 1250.5, "db_operations": 4, "n_plus_one": true }
    ],
    "spans": {
      "kept": 120,
      "kinds": [ { "kind": "sql", "count": 96, "total_us": 48210, "max_us": 2100, "last_at": 1792648788 } ]
    }
  },
  "security": {
    "events_total": 17,
    "active_bans": 2,
    "counters": { "rate_limit_blocks": 40, "login_jail_bans": 3, "honeypot_traps": 2, "…": 0 },
    "events": [ { "type": "LOGIN_JAIL_TRIGGERED", "at": 1792648795 } ]
  }
}
```

- **Request traces** are summaries of single requests, newest first, at most
  50: the time, the normalized method and matched route pattern (the same
  labels as `http.routes`), the status, the duration to the response headers
  in milliseconds (rounded to thousandths), the outermost ORM operations the
  request started and whether it repeated one at least the N+1 threshold. They
  are sampled: at most one ordinary request every 100 ms, and separately at
  most one outlier (a `5xx` or a request taking at least one second) every
  10 ms, so slow and failing requests stay visible under load.
  `sampled_total` counts the summaries kept since start.
- **Span totals** summarize the process's
  [`SpanCollector`](https://docs.rs/rullst-core/latest/rullst_core/telemetry_spans/)
  (records your code submits): count, total and longest duration and latest
  time per kind (`http`, `sql`, `ai`, `job`, everything else as `other`).
  Span names are free text that may contain SQL or paths, so they are never
  sent.
- **Security radar** reads the process's
  [`SecurityStore`](https://docs.rs/rullst-core/latest/rullst_core/security/struct.SecurityStore.html),
  which the `rullst-security` layers record into: every counter (rate-limit
  and lockout refusals, Login Jail lockouts, honeypot and deception hits,
  RBAC denials, refused cross-site WebSockets, schema violations, blocked
  prompt injections and the rest), the number of active honeypot bans, the
  events recorded since start (`events_total`, which keeps counting after the
  buffer of 50 drops the oldest) and the type and time of each kept event
  (`RASP_PAYLOAD_INTERCEPTED`, `LOGIN_JAIL_TRIGGERED`, …). An event's
  details and client address stay on the server, like the banned addresses.

Version 1 is unchanged, so existing clients keep working; read version 2
when you want the new sections.

## Watch your projects from Studio

The standalone Studio runs on your machine, without an application process,
and shows the document of each project you add: overview (radar, request
rate, error rate, latency), routes, queues, N+1 findings and, from an
application on 13.0.0-alpha.6 or later, request traces and the security
radar, with a project switcher in the header. It only connects outwards to your projects; nothing
new is collected or stored on the servers.

```bash
cargo install rullst-studio --version =13.0.0-rc.1 --no-default-features --features remote --locked
rullst-studio                  # prints http://127.0.0.1:5556/studio?key=…
# or, with the CLI installed:
cargo rullst studio --remote   # --port 7000 for another port
```

Pin the version: a plain `cargo install rullst-studio` selects the
end-of-life 12.3.0, which has no `remote` feature. The `remote` feature is not
enabled by default: applications that mount
Studio's local pages in development do not build its HTTP client, encryption
or SQLite history. `--no-default-features` leaves out the default
features, which only the local pages use: the database drivers, the SQLite
queue and the revenue dashboard (`capital`). The remote mode needs none of
them, so the installation compiles less: it builds no `rullst-orm`,
`rullst-capital` or `rullst-security`, and its only database driver is
SQLx's SQLite, for its own history.

It listens on `127.0.0.1` only, with the same protections as Studio's local
pages: loopback peer and `Host`, same-origin forms, and a per-process form
token. Other accounts on the machine can connect to `127.0.0.1` too, so each
start prints its address with a random key: open that address (it sets a
session cookie and drops the key from the address bar); without it every page
answers `403`. The key changes at every start, and anyone who can read the
printed address can use Studio until then, so keep that output private. The
session cookie carries the key, and browsers send it to every other server on
`127.0.0.1` they visit, because cookies are not kept apart by port; a server
another account runs there could then use Studio. Do not open local servers
you do not trust in that browser while Studio runs. Its pages are the remote ones only: the data browser, `.env` viewer,
AI and API playgrounds and migration pages do not exist in this mode.

### Add a project

On the **Projects** page, enter a name, the project's base URL and one of the
tokens of its `RULLST_MONITOR_TOKENS`; give each machine its own token, so you
can revoke it alone. Studio reads `<base URL>_rullst/monitor/v2`; when the
application answers `404` there (Rullst before 13.0.0-alpha.6), it reads
`<base URL>_rullst/monitor/v1` instead and tries version 2 again after ten
minutes. The **Traces** and **Security** pages then say that the application
serves version 1 only.

- The base URL must use `https://`, or `http://` to a loopback address such as
  `http://127.0.0.1:9000` (an SSH tunnel). User information, query strings and
  fragments are refused. Certificates are always validated.
- The token is sent only as `Authorization: Bearer` to that origin. Studio
  follows no redirect (a redirect is shown as a status), connects directly
  unless you [choose a proxy](#through-a-proxy), and reads at most 1 MiB
  within 5 seconds.
  Anything else (an unreachable host, `401`, `426`, an invalid document) is a
  status on the page, never the remote body.
- Every value from a project is HTML-escaped: a hostile or compromised
  application cannot run script in Studio.

### Where your tokens are kept

| File | Location (Linux and macOS / Windows) | Contents |
| --- | --- | --- |
| Project list | `$XDG_CONFIG_HOME/rullst/studio/projects.json` (default `~/.config/…`) / `%APPDATA%\rullst\studio\projects.json` | Names, base URLs, encrypted tokens, Studio settings |
| Key | `$XDG_DATA_HOME/rullst/studio/projects.key` (default `~/.local/share/…`) / `%LOCALAPPDATA%\rullst\studio\projects.key` | 32 random bytes |
| History | `$XDG_DATA_HOME/rullst/studio/history.sqlite` / `%LOCALAPPDATA%\rullst\studio\history.sqlite` | Aggregates of watched projects and fired alerts |

Both are created owner-only (`0600` in `0700` directories on Unix) and never
followed through a symlink; Studio warns when either is readable by other
users. Each token is encrypted with AES-256-GCM and bound to its project name
and base URL: if someone edits the URL in the file, the token no longer
decrypts and is never sent to the new address (remove and add the project
again). A copy of the project list alone (a dotfile repository, a backup of
`~/.config`) reveals no token. Malware running as your user can still read
both files; the operating system keychain is not used.

### Studio versions that share the project list

Several Studio versions can use the same project list (a newer `rullst-studio`
next to an older one, or after a downgrade). Since 13.0.0-alpha.6:

- **Fields of a newer Studio are kept.** A Studio reads a project list that a
  later 13.x Studio wrote, uses the fields it knows and writes the others back
  unchanged when it saves, so a newer Studio's settings and alert rules
  survive an older one. Unknown fields are bounded: at most 32 per object,
  names of at most 64 bytes and 16 KiB of JSON per object, and the whole file
  at most 256 KiB; Studio refuses a file over these bounds.
- **Known fields are still checked.** Names, base URLs, alert thresholds and
  notification settings must be valid, as when you save them, or the file is
  refused as malformed. The proxy setting is checked when it is used: a
  choice this Studio cannot apply (a proxy mode it does not know, a SOCKS URL)
  is kept as written and stops every connection, with a status on the
  Settings page that says why, until you choose another one there.
- **`version` changes only with an incompatible format.** It is `1`. A later
  13.x Studio only adds fields and never raises it. A Studio refuses a list
  with a higher version, without changing it, and names the Studio that reads
  it, for example "the project list uses file format 2, which needs Rullst
  Studio 14 or later; this Studio (13.0.0) reads format 1".
- **Studios older than 13.0.0-alpha.6 refuse any field they do not know.**
  13.0.0-alpha.6 and later write a new setting only when it differs from its
  default, so an alpha.5 Studio keeps reading the list until you enable
  desktop notifications, choose a proxy, or set a p99 or security-events alert
  rule. Update every Studio that reads the same list before you do.

### History and alerts

On the **Alerts** page, tick **Watch** for a project: while Studio runs, it
reads that project every 60 seconds and keeps, per poll, only aggregates the
document already contains: whether it answered, requests per second, window
requests, 5xx rate, p95 and p99 latency, the pending and failed totals of its
queues and, from a version 2 document, the security events recorded since
start. Routes, queue names and other labels are not stored. The **History**
page charts them for the last hour, day or week. Samples older than seven
days, beyond 10,080 per project (a week at one per minute) and alerts beyond
the newest 500 are deleted on every write; removing a project deletes its
history. Nothing new is collected on the server.

Each project has alert rules, all off by default:

| Rule | Fires when |
| --- | --- |
| Unreachable | the project cannot be read (any status on the overview page) |
| 5xx rate | the window's 5xx share reaches the percentage, with at least 20 requests in the window |
| p95 latency | the window's p95 reaches the milliseconds |
| p99 latency | the window's p99 reaches the milliseconds (since 13.0.0-alpha.6) |
| Pending jobs | the pending jobs of all its queues reach the count |
| Queue failures | this many jobs failed between two polls (a server restart, which resets the counters, never fires it) |
| Security events | the application recorded this many security events between two polls (a version 2 document is needed; a restart never fires it; since 13.0.0-alpha.6) |

A rule fires again for the same project only after its cool-down (15 minutes
by default, 1 to 1,440). Alerts appear on the Alerts page, with a badge until
you acknowledge them. Optionally, each alert is posted once to a webhook you
configure (Slack, Teams, a chat bot, your own receiver):

```json
{"source": "rullst-studio", "project": "shop", "rule": "p95_latency",
 "message": "shop: p95 latency 412.3 ms (threshold 250 ms)", "at": 1792648800}
```

The webhook URL is a secret like a token: it is encrypted in the project list
and never shown again. It must be `https://` without user information. The
post follows no redirect, uses the [proxy setting](#through-a-proxy) and gives up after five
seconds; the outcome (`delivered`, `failed: HTTP 500`, `failed: timeout`…) is
recorded on the alert, and it is not retried. Alert text is Studio's own
wording with the project name and numbers, never labels from the remote
document. Polling stops when Studio stops; for alerts around the clock, run
`rullst-studio` on an always-on machine or keep using your existing uptime
monitoring.

### Desktop notifications

Since 13.0.0-alpha.6, alerts can also appear as notifications of your
operating system. On the **Settings** page (`/studio/settings`), tick
**Show alerts as desktop notifications**, save, and press **Allow in this
browser** once; the browser asks for permission for Studio's own origin
(`http://127.0.0.1:5556`, which browsers treat as a secure context). Every
Studio page then asks Studio for new notifications every 15 seconds and shows
them through the browser's Notifications API; clicking one opens the Alerts
page.

- **What fires them:** the alert rules above, for watched projects. The text
  is the alert's own (Studio's wording with the project name and numbers).
- **Debounce:** a project is notified at most once per quiet period (10
  minutes by default, 1 to 1,440). Alerts in between are held and counted:
  the project's next notification mentions them, and when the period ends
  without one, a summary notification does. This comes on top of each rule's
  cool-down.
- **Where it works:** a Studio page must be open in a browser (a background
  tab is enough; browsers may then check about once a minute). Studio keeps
  at most the newest 32 notifications, a page that opens later shows none of
  the older ones, and several tabs show each notification once. The setting
  is kept in the project list; the permission belongs to the browser and can
  be revoked in its site settings.

Studio uses the browser instead of a native notification library: it already
serves its pages to your browser, the browser's permission prompt is the
consent, and it works the same on Linux, macOS and Windows without system
libraries or a background service.

### Reaching private servers

Studio does not open tunnels itself. Use the tool you already trust:

- **SSH tunnel:** `ssh -N -L 9000:127.0.0.1:3000 deploy@server`, then add
  `http://127.0.0.1:9000`. On the server, call
  `Monitor::allow_loopback_plaintext(true)` so the application accepts the
  tunnel's plain HTTP from loopback in production.
- **WireGuard or Tailscale:** the monitor still requires TLS evidence in
  production, so put the application's reverse proxy (with HTTPS) on the VPN
  address, or use `tailscale serve` to publish it over HTTPS, and add that
  `https://` URL. Restrict `/_rullst/monitor/` to the VPN range in the proxy.

### Through a proxy

Since 13.0.0-alpha.6, the **Proxy** section of the Settings page decides how
Studio reaches your projects and webhooks:

| Choice | Behaviour |
| --- | --- |
| Connect directly (default) | Proxy variables are ignored, as before. |
| Use the proxy variables of Studio's environment | The variables of the environment that started `rullst-studio`, chosen by the target's scheme as curl and reqwest choose them: `HTTPS_PROXY` (else `ALL_PROXY`) for `https://`, `HTTP_PROXY` (else `ALL_PROXY`) for `http://`, except for the hosts of `NO_PROXY`. Each is read upper case first, then lower case (`https_proxy`, `http_proxy`, `all_proxy`, `no_proxy`); a blank one counts as unset. Without them, connections are direct. |
| Use this proxy | An `http://` or `https://` proxy URL saved in the project list, without a user name or password, and an optional exception list. |

- In practice only `https://` connections use a proxy, as an HTTP `CONNECT`
  tunnel: the proxy relays the TLS stream and sees the host and port, never
  the token, the path or the document. Certificates are still validated
  against the monitored host.
- Plain `http://` connections, which Studio makes only to loopback (an SSH
  tunnel), and connections to a loopback host (`localhost`, `127.0.0.0/8`,
  `::1`) are always direct, so `HTTP_PROXY` never changes where Studio
  connects; Studio still checks it.
- A proxy URL is `http://` or `https://` with a host and an optional port;
  a value without a scheme (`proxy.internal:3128`) means `http://`, as curl
  assumes. **SOCKS proxies (`socks5://`, `socks5h://`, `socks4://`) are not
  supported**: such a value is refused and named on the Settings page (for
  example "ALL_PROXY names a SOCKS proxy, which Studio does not support"),
  never ignored. Reach a SOCKS-only network through an HTTP proxy in front of
  it, or an SSH tunnel to the application (above).
- Exceptions use the `NO_PROXY` syntax: host names, which also match their
  subdomains (a leading dot is optional), IP addresses, CIDR ranges such as
  `10.0.0.0/8`, or `*` for every host, separated by commas or spaces (at
  most 4,096 characters). They apply to both schemes.
- A proxy that needs a password comes from the environment
  (`HTTPS_PROXY=http://user:password@proxy:3128`, or `HTTP_PROXY` and
  `ALL_PROXY`); Studio never stores it, and the Settings page shows only the
  proxy's scheme, host and port.
- When a variable or setting that Studio would use cannot be used (a SOCKS or
  malformed URL in any of the variables above, or exceptions over 4,096
  characters), Studio connects to nothing: the Settings page names the
  variable or setting, and every project shows "the proxy setting cannot be
  used", instead of quietly connecting directly. A variable that no target
  uses (`ALL_PROXY` when both `HTTPS_PROXY` and `HTTP_PROXY` are set) is not
  read.
- A change applies to the next read, without restarting Studio; a change of
  the environment needs a restart of `rullst-studio`.

## Limits

- Each process reports itself. Behind a load balancer, each replica has its
  own counters, budgets and lockouts, and a poll reaches one of them; poll
  replicas individually if you need all of them.
- Counters restart with the process.
- The development hot-reload server does not mount the monitor.
- A panic that aborts the connection is not counted.
- The schema is versioned: fields are only added in a new version, served
  next to `v1` at a new path.

## Overhead

Collection runs on every request once the monitor is mounted: it reads the
matched route, takes a read lock on the route table, updates that route's
counters under its own lock, and gives the request a scope in which ORM
operations are counted. Trace sampling adds one atomic read per request; the
summary buffer's lock is taken only for a kept request, at most about 110
times a second. Measured on an 8-thread Linux machine in a release
build (`cargo test --release -p rullst-core --lib monitor::overhead_tests --
--ignored --nocapture --test-threads=1`, from a clone of the Rullst
repository): a trivial Axum route took 0.72 µs per request without
the recorder and 1.32 µs with it, so about **0.6 µs per request**; the
statistics update alone took about 96 ns, and 70 to 80 ns per call with 4 to 8
threads recording at once. Memory is bounded: about 1 KiB per route pattern
(273 KiB for 257), 64 N+1 entries, and the endpoint's per-client limiters,
which keep at most 100,000 clients each like Core's `RateLimiter`.
