## The short version

As engineering, Rullst is unusually rigorous for a framework of its size and age,
and unusually honest about its limits. As a product, it is still young: one
maintainer, a fast-moving API and, as far as I can see, little validation
outside the maintainer's own applications. 13.0 is the release where that can
start to change, if the 13.x API stays stable.

## What stands out

- **Evidence over claims.** The project runs 34 workflow definitions, among
  them:
  - 42 libFuzzer targets in 11 fuzz crates;
  - Miri and Kani on selected code, and thread and address sanitizers;
  - property tests;
  - a pull-request mutation gate for the CLI;
  - an enforced 90% line-coverage floor;
  - zero-panic and `unsafe` policies;
  - SBOMs with build-provenance attestations.

  A release is admitted only at an exact commit that passed about two dozen
  required workflows. Few Rust web frameworks I know of, including far larger
  ones, do this much.
- **A culture of saying what is not done.** Every release lists its known
  limitations. The [capability ledger](capability-ledger.md) records abandoned
  ideas and why. [Maturity tiers](maturity.md) separate Core from Extension and
  Experimental. The documentation keeps saying "evidence for the stated scope,
  not a certification". This is rarer than it should be, and it is the
  strongest reason to trust the project.
- **Batteries that are secure by default.** CSRF, strict headers, a WAF with a
  development report-only mode, Argon2id, passkeys, revocable sessions and
  signed webhooks are wired in, not left as exercises. Removed features are
  removed loudly: `cargo rullst upgrade` has a rule for each one.
- **Built to be read by tools.** It favours explicit APIs and compile-time
  macros over runtime reflection, and it has typed errors. Every generated
  project gets an `AGENTS.md`, the site publishes `llms.txt`, and CLI data
  output follows one `--json` contract. This helps humans as much as AI
  assistants.
- **A tested path to production.** `cargo rullst deploy` produces a hardened
  Dockerfile, `compose.yaml` and Caddyfile. CI builds and starts them with
  Docker and rootless Podman, and checks HTTPS, the container hardening,
  migrations and persistence. Writing that test found two real bugs that every
  SQLite deployment would have hit.

## Where it is weaker

- **Bus factor.** Twenty packages, a CLI with dozens of generators and a large
  CI estate are maintained by one person. This is the biggest risk to anyone
  who adopts Rullst. It matters more than any bug.
- **Breadth ahead of validation.**
  - Several integrations are tested only against offline mocks: the OAuth
    providers, Stripe beyond test mode, Bunny Stream, the mail providers.
  - Five packages are Experimental: IoT, Privacy, Supervision, Media and Labs.
  - The provider deployment guides were written from the providers'
    documentation, not followed end to end on real accounts.
  - Whatever is broad but unvalidated becomes maintenance load without
    becoming trust.
- **Documentation drifted behind the code.** Before this release, the
  documentation audit corrected dozens of inaccuracies across the book. It also
  found about ten first-hour breakages that no test caught; for example,
  `cargo rullst auth` refused to run on every freshly generated starter. CI
  now builds and runs the generated deployment, and runs the commands of the
  first-hour pages (the README quickstart, getting started, the first
  tutorials and the REST API quickstart) as written. The lesson stands: in
  this project, code changes faster than its prose.
- **Churn.** v12 reached end of life on 16 October 2026, and v13 changes a
  lot: removed generators and providers, a leaner CLI, `FromRow` generated by
  `#[derive(Orm)]`, a single TLS crypto provider. Each change is reasoned and
  documented. But adopters judge a framework by how rarely it makes them
  migrate. The 13.x line needs to hold still.
- **First builds are still slow.** A generated starter's first build takes
  about two to two and a half minutes on the measuring machine (see
  [build times](build-times.md)). Most of it is cryptography (the `aws-lc-sys`
  build script), SQLx and the framework itself. Later builds are much faster.
- **Process weight.** A full release admission takes about 17 hours of
  fuzzing. Release fuzz evidence is now derived from each fuzz package's build
  graph, so a change to the documentation, the CLI or the examples no longer
  reruns it, but a change to a book page that the facade's doctests include
  still reruns the facade's 12 targets. The rigor is real, but so is its cost
  for a single maintainer.
- **Unknown adoption.** I have no data on external users, production
  deployments or community size. I have not counted them, and you should not
  assume there are many.

## Is it right for you?

**Consider Rullst if:**
- you want a batteries-included Rust web framework, with server-rendered HTML,
  HTMX and JSON APIs, and secure defaults you don't have to assemble;
- you are building a SaaS or an internal tool on SQLite, PostgreSQL or MySQL,
  with Stripe billing and email;
- you value documented limits and CI evidence over a large ecosystem;
- you are comfortable pinning an exact version and reading migration guides.

**Look elsewhere, or wait, if:**
- you need a long production track record, a large community or commercial
  support today; wait for 13.0.0 and a few stable 13.x releases at least;
- your frontend is a heavy client-side SPA, which Rullst deliberately does not
  center on;
- you depend on providers Rullst no longer ships (see the
  [v13 migration guide](migration-v13.md)), or on the Experimental packages for
  anything safety-critical;
- you prefer to assemble a minimal stack yourself; plain Axum with crates you
  choose may suit you better.

## What would raise my confidence most

1. A 13.x line with no breaking changes for months. The public-API review and
   the SemVer gate exist for this.
2. A second maintainer. `GOVERNANCE.md` already records a successor
   arrangement; an active co-maintainer would reduce the risk further.
3. Real-account validation of the OAuth, payment and deployment paths.
4. External users and case studies, beyond the maintainer's own applications.
5. Fewer Experimental packages, each either promoted or retired with evidence.
