02 / Security, by default and by test

More protections on by default.
More automated verification.

What a generated application starts with, what you add when you need it, and what CI runs against the framework's own code. None of it proves that an application is secure: its authorization rules, provider settings and deployment stay yours.

01 / ON BY DEFAULT

In every generated application

  • Secure headers with a per-request CSP nonce, in every environment.
  • CSRF protection (a double-submit token) on write routes, in every environment.
  • A WAF that refuses suspicious requests in staging and production and only logs them in development. The generated Dockerfile, Compose and Kubernetes files set RULLST_ENV=production.
  • Security tests: each project's src/security_tests.rs checks the headers, CSRF and the WAF under the production baseline with cargo test.
  • Production checks: the API starter does not start without API_TOKEN, and the generated billing code refuses an empty payment key in production. In 13.0.0-rc.1 (not yet released), mail, AI and the Turso starters also refuse empty settings in staging and production instead of using an offline mock, and CI fails on any such fallback no one reviewed.
What each starter mounts ↗
02 / OPT-IN

When your application needs them

  • Passkeys (WebAuthn) in rullst-auth, with an optional shared PostgreSQL ceremony store.
  • OAuth2/OIDC sign-in: cargo rullst make:oauth for Google, GitHub, Microsoft or Apple.
  • Two-step verification with TOTP and recovery codes: cargo rullst make:mfa.
  • A login jail (LoginGuard) and more layers in rullst-security: honeypot paths, response secret masking, a WebSocket origin guard and JSON schema guards.
Recommended production stack ↗
03 / VERIFIED IN CI

Automated checks on the framework's code

  • 42 fuzz targets (libFuzzer), required as release evidence.
  • Mutation testing of each pull request's changed lines (not a required check), plus manual campaigns.
  • Miri and Kani on selected critical code, weekly and for each release.
  • ThreadSanitizer and AddressSanitizer, daily.
  • OWASP ZAP scans of the generated REST API, SaaS starter and LMS example: blocking, with seven explained rules reported as INFO.
  • CodeQL analysis of the Rust and JavaScript code.
  • Dependency audit: RustSec advisories, licenses and sources on every change and twice a day.
  • No unwrap, expect or panic! in production code, denied by Clippy.
All 36 workflows and their exact scope ↗

How the defaults compare: Loco (loco-rs 1.3.1) documents secure-headers middleware that is disabled by default and no CSRF middleware; Topcoat (topcoat 0.12.1) rejects cross-origin state-changing requests by default and documents no secure headers or CSRF tokens. Checked on 21 November 2026; see them side by side.

Review. Rullst has one maintainer, and pull requests need no second reviewer. AI-assisted review and automated checks are not independent human review, and no external audit has been completed. Security assurance case ↗ External audit kit, for reviewers ↗ Report a vulnerability ↗

Parts that ship with the framework, each documented with what it was tested against and what it does not do. Twenty packages share one version; the specialized ones are optional Extension packages.

What a card says about Loco and Topcoat was checked on 21 November 2026 in Loco loco-rs 1.3.1 and Topcoat topcoat 0.12.1, their latest releases then.

CLI · RESOURCES

cargo rullst footprint

Measures your application's binary size, idle memory, start-up time, CPU time per request and page weight, says how it measured each one, and can fail CI when a budget grows. Its carbon figure is an SCI estimate from inputs you give, not a measurement.

Loco and Topcoat document no such command.

Footprint guide ↗
CLI · UPGRADES

cargo rullst upgrade

--dry-run lists each source change a newer Rullst needs, at file:line, with a rule code and its migration-guide row; applying backs up the files, updates the versions and runs cargo fix and cargo check. It does not migrate data.

Loco documents an upgrade guide and no upgrade command; Topcoat documents neither.

Assisted upgrades ↗
CLI · TESTS

Tests from the first commit

Every project cargo rullst new creates has a smoke test of each page (status, security headers, HTML hygiene) and, unless you pass --no-ci, a CI workflow with Clippy, tests, cargo audit and a secret scan. cargo rullst add browser-tests opens every page in Chromium, Firefox and WebKit with axe-core.

Testing your application ↗
DEVELOPMENT · STUDIO

A developer control room

Studio runs as a local debug server on 127.0.0.1:5555: a database inspector with an ER diagram, queues, feature flags, request traces and the security events of the running process.

Loco and Topcoat document no development dashboard.

Studio guide ↗
ADMIN · NEXUS

A generated admin

Nexus builds server-rendered list, search, create, edit and batch views for the ORM models you register, with field policies and RBAC; release builds need your application's sign-in or Basic Auth over TLS.

Loco and Topcoat document no generated admin (Topcoat has a hand-written admin demo).

Nexus guide ↗
BILLING · CAPITAL

Payments with fail-closed checks

Stripe and InfinitePay adapters, signed webhooks with replay protection, quotas, entitlements and invoices in minor units. The generated billing code refuses empty payment keys in production.

Loco and Topcoat document no payments.

Billing guide ↗
MAIL

Transactional mail

Resend, AWS SES, SendPulse or SMTP, sent in the background, with recipient suppression and opt-in attachment inspection. In 13.0.0-rc.1, a missing provider key in staging or production is an error, not a send that only looked successful.

Mail guide ↗
AI

One guarded AI client

Gemini, OpenAI, Claude and OpenAI-compatible endpoints (DeepSeek and Ollama presets), with a prompt-injection filter, PII masking and offline fixtures for tests.

Provider boundaries ↗
IOT · SIGNED OTA

Firmware updates you can verify

no_std telemetry helpers, MQTT 5 and CoAP encoders and Ed25519-signed OTA manifest verification with a rollback-counter contract, run on a BBC micro:bit V2. Transports, flashing and bootloaders stay the application's.

Loco and Topcoat document no IoT or OTA support.

IoT guide ↗
LABS

Graded exercises, your runner

Contracts for exercise jobs that a separately deployed runner claims: leases, cancellation, retention and signed receipts. Labs itself never runs learner code.

Runner contract ↗
PRIVACY

Age policies and consent

Proportional age policies, signed threshold attestations and versioned consent and withdrawal, on SQLite or PostgreSQL; make:age-gate and make:privacy wire them into an application. No live age provider is included.

rullst-privacy ↗
SUPERVISION

Transparent exam supervision

Exam and parental contracts with an explicit collection acknowledgement, typed browser observations and camera-presence and audio-activity adapters. No media model, automatic grading or device-wide control is included.

Supervision guide ↗

Core packages are in every application; Extension packages are optional and carry the same 13.x stability promise for their documented scope (maturity tiers). Scope and limits lists what Rullst does not do and what its tests cannot establish.

Recipes, not integrations. MongoDB, DuckDB and Qdrant are application recipes: your code uses their official crates directly. Their built-in adapters were removed in 13.0.0-alpha.5. Other services are application code too: write an adapter on the provider trait (payments, mail, video) or follow a recipe. Read the recipes ↗

The maintainer's production applications Academy, capoeira and vene.win run on real domains on one Oracle Ampere A1 Arm machine behind a shared Caddy with Let's Encrypt certificates. CI tests the generated deployment on x86_64 only; Arm machines are not tested in CI. Deployment limits ↗

v13 is in prerelease: 13.0.0-alpha.6 is the 13.0 feature freeze, followed by 13.0.0-rc.1 (fixes and documentation, and the changes the maintainer approved one by one after the freeze, two of them breaking) and 13.0.0. Cargo never selects a prerelease on its own, so name the exact version from crates.io (=13.0.0-alpha.6) and use its matching immutable tag rather than the moving main branch. The v12 line reached end of life on 16 October 2026 with 12.3.0, and the v12 branch is frozen; move applications with the v12 → v13 adoption guide. The legacy v5 branch is no longer maintained either. Scope and limits lists what Rullst does not do by design and what its own tests cannot establish. Prerelease and stable describe the framework API lifecycle, not automatic approval of an application's authorization, provider configuration, operations or deployment.
