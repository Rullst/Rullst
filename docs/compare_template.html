Three Rust web frameworks. Checked facts.

Rullst, Loco and Topcoat.

All three build web applications in Rust on Tokio, and each one is the better fit for some projects. This page compares them topic by topic, using what each project's own documentation says. Where a project does not document something, the page says so instead of guessing.

Checked on 14 November 2026 against Rullst 13.0.0-alpha.5, Loco loco-rs 1.3.1 and Topcoat topcoat 0.12.1. Rullst's maintainer wrote this page. If a fact is wrong or out of date, please open an issue.

Where each one fits

  • Rullst

    A good fit when you want one coordinated suite on Axum and SQLx that already includes sessions and passkeys, CSRF protection, billing (Stripe and InfinitePay), transactional mail, a model admin and a local developer control room, with server-rendered HTML.

    Keep in mind: 13.0 is still a prerelease, and the project was first published in May 2026 by its sole maintainer.

  • Loco

    A good fit when you want a stable 1.x release with Rails-style conventions, Sea-ORM, JWT or cookie authentication, job queues on Redis, PostgreSQL or SQLite, and generators for models, scaffolds and workers. It has the largest community of the three.

    Keep in mind: payments and an admin UI are not part of its documentation.

  • Topcoat

    A good fit when you want server-rendered components whose $(...) expressions also run in the browser as generated JavaScript, with no Wasm bundle and no client build step.

    Keep in mind: its README calls it early-stage and experimental; authentication, background jobs and deployment docs are on its roadmap.

Topic by topic

Rendering model

Rullst
Server-rendered HTML from the html! macro, escaped by default, with htmx and the CSP build of Alpine.js for interactivity. No client bundle by default.
Loco
Server templates with Tera 2 behind a swappable renderer. Also a client-side SPA mode (Vite and React) and a single-binary mode with embedded assets.
Topcoat
Server rendering with the view! macro and async components. $(...) expressions are type-checked Rust, also translated to JavaScript for reactivity in the browser. Optional htmx, Alpine AJAX and Datastar integrations.

Database and ORM

Rullst
Its own ORM (#[derive(Orm)]) on SQLx for SQLite, PostgreSQL and MySQL/MariaDB, with Schema migrations. Turso/libSQL, SurrealDB and Redis data structures through separate adapters.
Loco
Sea-ORM 2.0 with migrations. The documented database drivers are SQLite and PostgreSQL.
Topcoat
No ORM in the topcoat crate. topcoat new --database toasty generates an app that uses Toasty on SQLite, with Toasty's migrations.

Authentication and security defaults

Rullst
Argon2 password hashing, encrypted sessions, passkeys, RBAC and OAuth2/OIDC sign-in. The SaaS starter wires CSRF middleware; rullst-security also provides secure headers, a WAF layer and a login jail.
Loco
JWT by default, with argon2 hashing and API keys. Opt-in signed or encrypted cookie sessions and OAuth2/OIDC with GitHub and Google presets. Secure-headers middleware exists but is disabled by default; CSRF middleware is not documented.
Topcoat
Session tokens with storage you provide, in __Host-, Secure, HttpOnly, SameSite=Lax cookies. A default origin policy rejects cross-origin state-changing requests. Authentication is on the roadmap; password hashing, secure headers and CSRF tokens are not documented.

Background jobs

Rullst
Queues in rullst-core (in-process, SQLite and Redis). rullst-messaging adds retries, dead-letter queues, an outbox relay and Redis Streams messaging.
Loco
Queues on Redis, PostgreSQL or SQLite, in-process modes, and a cron-like scheduler.
Topcoat
Not built in. Background jobs are on the roadmap.

Mail

Rullst
rullst-mail: templated mail through Resend, AWS SES, SendPulse or SMTP, delivered in the background, with recipient suppression and a conformance kit for your own transport.
Loco
A built-in SMTP mailer that sends through the job queue, with a stub mode for tests. An opt-in notifications feature adds Slack and webhooks.
Topcoat
An opt-in mail feature with SMTP, file (.eml) and in-memory transports.

Payments and billing

Rullst
rullst-capital: Stripe and InfinitePay adapters, verified webhooks with replay protection, quotas, entitlements and invoices.
Loco
Not documented.
Topcoat
Not documented.

Admin and observability

Rullst
Nexus, an admin generated for registered models; Studio, a local developer control room; OpenTelemetry export for distributed traces, tested in CI against an OpenTelemetry Collector in a local container.
Loco
No admin UI documented. Logging with tracing, /_ping, /_health and /_readiness endpoints, and cargo loco doctor.
Topcoat
No admin framework (an admin demo app exists). Logging and health endpoints are not documented; OpenAPI generation arrived in 0.12.1.

CLI and generators

Rullst
cargo rullst new (Blank, API and SaaS starters) and make:* generators for models, migrations, controllers, resources, workers, mail, billing, MFA, OAuth and more; dev, doctor and assisted upgrade.
Loco
loco new (SaaS, REST API, lightweight and advanced templates) and cargo loco generate for models, migrations, scaffolds, controllers, tasks, workers, mailers and deployment files.
Topcoat
topcoat new, dev, fmt, ui (copies components into the project), asset bundle and l10n check. Model or controller generators are not documented.

Deployment guidance

Rullst
Guides for DigitalOcean, Hetzner, Oracle Cloud and Google Cloud. CI tests the generated VM deployment of the Blank and SaaS starters, on SQLite, with Docker and Podman on an x86_64 runner; Arm machines are not tested, and the provider guides were written from the providers' documentation, not followed end to end on real accounts.
Loco
A release binary, plus generated Docker, nginx or AWS Lambda setups, and loco doctor before going live.
Topcoat
Deployment docs are on the roadmap. A Cloudflare Workers example, and custom hosting through serve() or Router::handle.

Stability, versioning and support window

Rullst
13.0 is in prerelease; 13.0.0-alpha.6 froze its features and public API, and 13.0.0-rc.1 adds fixes, documentation and the changes the maintainer approved one by one after the freeze, two of them breaking. After 13.0.0, the maintainer intends to keep 13.x the active line for 12 months, then give it security fixes for 1 to 3 more months after 14.0.0 (an intention, not a guarantee). Semantic Versioning; MSRV Rust 1.96.
Loco
1.0.0 (July 2026) was its first stable release. Upgrade notes list breaking changes; a semver statement and a support window are not documented. MSRV Rust 1.94.
Topcoat
Its README says: early-stage and experimental, expect breaking changes. Its changelog says it follows Semantic Versioning. No support window documented. MSRV Rust 1.99.

Maturity and community

Rullst
First published in May 2026. MIT license. 21 GitHub stars and 7 contributors on 14 November 2026.
Loco
First release in November 2023. Apache-2.0 license. 9,629 GitHub stars and 157 contributors on 14 November 2026.
Topcoat
Repository created in April 2026, first functional release in July 2026, in the tokio-rs GitHub organization. MIT license. 7,221 GitHub stars and 41 contributors on 14 November 2026.

Why not Leptos or Dioxus?

Checked on 19 November 2026 against Leptos leptos 0.8.23 and Dioxus dioxus 0.7.10.

Leptos and Dioxus are full-stack in a different sense: they are UI frameworks. The same Rust components can render HTML on the server and then run in the browser as WebAssembly, which hydrates that HTML, and server functions let the browser call Rust code that runs only on the server. Dioxus also targets desktop and mobile.

As UI frameworks, neither ships an ORM, migrations or authentication, and neither documents mail, background jobs or an admin panel. The Leptos book says Leptos itself provides neither the HTTP server nor the database; the Dioxus documentation says Dioxus does not provide a built-in way of managing authentication, and its database tutorial uses rusqlite and names SQLx and SeaORM among the alternatives. Applications assemble these parts from other crates: the Leptos authentication example and the Dioxus authentication guide both use axum_session_auth with SQLx.

They are not in the Performance section because it measures equivalent applications serving HTTP requests. The server side of a Leptos application runs on Actix Web or Axum through Leptos's integrations, and Dioxus Fullstack is built on Axum, which is already the benchmark's baseline; an equivalent application would also need its ORM and authentication assembled by hand. The approaches are complementary: a Leptos or Dioxus interface can call a Rullst HTTP API.

Performance

These numbers are not written by hand: each daily build of this site inserts the latest published results of the Rullst/Benchmarks suite for the three frameworks, Actix Web and Gin, plus a minimal Rullst configuration. Rullst's maintainer also maintains that benchmark and wrote every implementation in it.

How to read these numbers

  • 1.00× is Axum. Every score divides a framework's result by the result of Axum, a small Rust framework used as the reference, measured on the same machine in alternating rounds. 0.50× is half of Axum's result and 2.00× twice. Higher is better in every score: for memory and start-up time the ratio is turned around, so a higher score means less RAM or a faster start.
  • Ties and ±. The machines are shared cloud machines, so results vary from run to run. "±6%" next to a score is the margin within which two scores cannot be told apart. Scores that close share a range of positions, such as "3–7": those implementations are in positions 3 to 7 in no particular order.
  • The categories answer different questions. Hello world: what a framework costs per request when the page is trivial. Database: how it reads, writes and renders rows. Application: what it does with a real request (input, validation, a write, a form with CSRF protection, a signed-in user). Memory: how much RAM it needs under load. Startup: how fast it starts. Stability (pass or fail): whether it keeps working under heavier load.
  • The database usually comes first. In a real application the database is usually the limit before the framework is, so a large gap in Hello world shrinks or disappears once requests read and write data; Database and Application are closer to what an application does.
  • The overall score is a summary. It combines the five category scores, with Hello world, Database and Application counted twice and Memory and Startup once, for quick reading. The categories are the real result: other weights change the order, as the full results show.
  • Rullst appears twice. "Rullst" is the application that cargo rullst new generates, with the production middleware it turns on: WAF, CSRF protection, secure cookies, security headers and an access log; it is the Rullst with a position. "Rullst (minimal)" is the same router, ORM and html! templates without those layers, served like the Axum app; it is a diagnostic, with scores and without a position. The gap between the two rows is what those layers cost.
