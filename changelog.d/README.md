# Changelog fragments

Every pull request with a user-visible change adds one file here instead of
editing the `## [Unreleased]` section of [`CHANGELOG.md`](../CHANGELOG.md).
Parallel pull requests then never edit the same lines, so merging one no longer
creates a conflict in the others. Release preparation merges the fragments into
the changelog and deletes them.

## Format

- One file per change: `changelog.d/<slug>.md`, where the slug uses lowercase
  letters, digits and hyphens (for example `make-pwa-mfa-test.md` or
  `612-surrealdb-create.md`). A pull request with changes in two categories
  adds two files.
- The first line is exactly one category heading: `### Added`, `### Changed`,
  `### Deprecated`, `### Removed`, `### Fixed` or `### Security`.
- Then one or more bullets, written exactly as `CHANGELOG.md` entries: plain
  English, what was wrong or what is new and what happens now, continuation
  lines indented by two spaces, a `**Breaking:**` prefix when it is one. No
  other headings.

Example, `changelog.d/make-pwa-mfa-test.md`:

```markdown
### Fixed

- After `cargo rullst make:mfa` and then `cargo rullst make:pwa`, the
  application's `cargo test` failed: `make:pwa` adds its same-origin
  `<script src="/static/pwa.js">` to the two-step verification pages, and the
  test generated by `make:mfa` refused any `<script`. That test now refuses
  only inline scripts.
```

Check your fragments with:

```bash
python3 .github/assemble-changelog.py --check
```

Pull requests do not need a fragment for changes that users do not see (CI,
tests, internal refactoring), and Dependabot pull requests never need one.

## Checks

The `Changelog fragment policy` job of
[`workflow-lint.yml`](../.github/workflows/workflow-lint.yml) runs on every pull
request. It validates the fragments and fails when the pull request adds lines
under `## [Unreleased]` in `CHANGELOG.md`. It is not a required check, but
pull requests are merged only with every check green. Release-preparation
branches (`chore/v<major>-release-<version>`, for example
`chore/v13-release-13.0.0-rc.1`) are exempt from the `[Unreleased]` rule.

## Release preparation

On the release-preparation branch, run:

```bash
python3 .github/assemble-changelog.py --release 13.0.0-rc.1 --date 2026-11-20
```

It appends each category's fragments, in file-name order, to that category's
`[Unreleased]` subsection (adding missing subsections in the order Added,
Changed, Deprecated, Removed, Fixed, Security), opens the dated version section
below the `[Unreleased]` introduction and deletes the merged fragments. Then
write the release summary and `### Known limitations` below the new heading.
A release is not admitted while fragments remain here:
`.github/release-preflight.py` and `.github/check-release-source.py` refuse it.
