# Small SaaS example

A reproducible Linux/SQLite example generated by the CLI from this Rullst
checkout. It demonstrates registration, login and an authenticated notes API
with explicit organization membership and resource ownership. The same source
is used by the `cli-saas-journey` CI diagnostic.

This is a development example for the unpublished v13 candidate. It is separate
from the [blog showcase](../blog/README.md) and from the independently maintained
[deployed SaaS](https://github.com/Rullst/examples/tree/main/blueprints/saas).
Its provider credentials are empty and its data is disposable.

## Run and explore

Requirements: Linux, Python 3.11 or newer, the repository's pinned Rust toolchain
and native build dependencies. Start from a checkout of the complete framework.
The first run downloads the locked Cargo dependencies and builds the CLI and
application; later compile operations run offline. No provider account is used.
The runner requires at least 32 GiB available on the source and temporary
filesystems, checks space during builds and stops owned builds at the 12 GiB
reserve. Prefer the hosted diagnostic on a workstation near the preventive
15 GiB threshold.

From the repository root:

```sh
python3 examples/saas/run.py --serve
```

The command installs the source CLI into a private temporary prefix, generates
the SaaS blueprint, adds the notes resource, runs migrations twice and checks
the generated application with strict Clippy. It prints a loopback URL, the
generated source directory and the database path. Open the printed `/register`
URL and create a disposable account using an address such as
`alice@example.invalid` and a password of 12–72 bytes.

Registration signs you in and opens the starter's dashboard. The notes resource
is a JSON API; it deliberately has no additional frontend or organization-admin
product. The debug starter may also run Studio on `127.0.0.1:5555`.

In another terminal, grant the registered account a membership using the
**database path printed by the running example**:

```sh
python3 examples/saas/membership.py \
  --database /path/printed/by/the/runner/journey.sqlite \
  --email alice@example.invalid --tenant org-a
```

This is an explicit local operator action against the disposable example
database. The command requires an existing account and database, uses bound SQL
parameters, and can be repeated without creating duplicate memberships. An
application must supply its own authenticated invitation/membership management;
there is no public route that accepts a claimed user or tenant as authority.

While signed in, run the following in the browser console on the example's
dashboard to create and read an owned note. Requests use the existing session
cookie and the real double-submit CSRF token:

```js
const csrf = document.cookie.split("; ")
  .find(cookie => cookie.startsWith("rullst_csrf="))?.split("=")[1];
const created = await fetch("/journey/notes", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-CSRF-Token": csrf,
    "X-Tenant-ID": "org-a"
  },
  body: JSON.stringify({ body: "My first note" })
});
if (created.status !== 201) throw new Error(`Create failed: ${created.status}`);
const note = await created.json();
const loaded = await fetch(`/journey/notes/${note.id}`, {
  headers: { "X-Tenant-ID": "org-a" }
});
console.log(loaded.status, await loaded.json());
```

`PUT /journey/notes/{id}` updates the same bounded `body` field with the same
headers. The server derives ownership from the authenticated user; extra
`owner_id` or `tenant_id` JSON fields are rejected. Use a separate browser
profile for another user so the two sessions do not share cookies.

Press **Ctrl+C** in the runner terminal to stop the owned application. Its
temporary source, installed CLI, build artifacts, keys and database are then
removed. Do not store valuable data in this demonstration. Interactive mode
records `passed: null`; exploring the application is not an automated test pass.

## Verify the same example

```sh
python3 examples/saas/run.py
```

Without `--serve`, the runner creates three synthetic users and drives real
loopback HTTP. It checks allowed registration/login/read/write, anonymous and
wrong-password denial, same-tenant ownership, cross-tenant isolation, forged
tenant hints, CSRF, input bounds, rejected mass assignment, unchanged state after
denial, persistence across a process restart, membership revocation and logout.
It stops and removes the temporary application when finished.

The default result is `saas-journey-result.json` in the checkout root; use
`--output /path/to/result.json` to select another existing directory. It records
the source and lock identities, CLI version/hash, phase timings and individual
outcomes without keys, passwords, cookies or database contents. In GitHub,
dispatch **Rust CI** with `platform=ubuntu-latest` and
`shard=cli-saas-journey`; its artifact retains this result even on failure.

## Source map and boundaries

| File | Responsibility |
| --- | --- |
| [run.py](run.py) | Source CLI installation, generation, configuration, migration, startup and cleanup. |
| [journey.rs](journey.rs) | Notes routes, database-backed membership, tenant selection and owner authorization. |
| [migration.rs](migration.rs) | SQLite tables inserted into a CLI-scaffolded migration. |
| [membership.py](membership.py) | Local operator membership command, also used by the automated journey. |
| [http_acceptance.py](http_acceptance.py) | HTTP acceptance with independent cookie jars and explicit negative cases. |

There is no second checked-in copy of the generated SaaS or another workspace
crate. The installed CLI supplies the starter; these small files supply the
application-specific resource and its repeatable verification. Changes to those
files are exercised by the same CI diagnostic.

The notes routes explicitly mount CSRF, secure headers and WAF, including in
the loopback development profile. Auth loads the user from the database before
membership resolution. `TenantLayer` accepts only a tenant in that membership;
when a user has a single membership, an omitted tenant hint can select it.
Queries bind tenant and resource identifiers; `RbacGuard` enforces ownership.
Membership is resolved again on each request. This does not promise immediate
cancellation of a request already authorized before a membership change.

The profile uses a source-installed **debug** CLI and development HTTP. It does
not establish production TLS/browser-cookie enforcement, live payments or mail,
stateless-session revocation, archive/registry installation, schema rollback,
load capacity or a comparison with another framework. Logout clears the client
cookie. Provider configuration, organization administration, deployment and
other production policies remain application responsibilities. See the
[evaluation plan](../../docs/src/v13-framework-comparison.md) for the broader
scope and evidence rules.
